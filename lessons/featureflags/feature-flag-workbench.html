Systems lesson 22 · Feature flags

Feature Flag Workbench

A feature flag ships new code switched off and lets you decide, at run time, who sees it. This lesson builds that idea three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, averaged over eight seeded runs at 8 requests per second from 200 users.

1. A bad feature at 50%

Experiment 1 of 5
Buggy feature on for 50% of users · someone notices at 30 s · flip the kill switch (servers refresh every 5 s) vs redeploy the old build (90 s pipeline, then 30 s per server)
How long until no user hits the bug, with each fix?

The new code was already on every server; the flag only decided who ran it. Turning the flag off needs no build, no pipeline and no restart: each server stops showing the feature at its next settings refresh. A redeploy has to rebuild and roll out server by server, and the bug keeps firing on every server that hasn't been replaced yet. That gap is the whole point of separating deploy from release.

2. Random or sticky

Experiment 2 of 5
30% rollout for 2 minutes · each request rolls a die vs each user is hashed to a fixed bucket
Out of about 200 users, how many see both the old and the new version?

With a die roll per request, a user who makes several requests lands in the 30% sometimes and outside it the rest, so the page changes under them: a button appears, then vanishes. Hashing the user id (plus the flag name) gives each user a fixed bucket from 0 to 99, so the same user always gets the same answer, and raising the rollout from 30% to 50% only adds users, never moves them back.

3. Stale flags

Experiment 3 of 5
Feature on for everyone, turned off at 30 s · each server refreshes its copy of the settings every 5 s vs every 60 s
With a 60 s refresh, how long do servers keep showing the feature after it's off?

Servers don't ask the flag service on every request; that would make it a dependency of every page. They keep a copy and refresh it. Until a server's next refresh it still serves what it last saw, so after a flip the feature fades out server by server. Shorter refreshes or a push from the flag service (streaming, webhooks) shrink that window; that is what makes a kill switch fast.

4. Flag debt

Experiment 4 of 5
3 flags vs 10 flags in use, each on for half the users (sticky, independent)
With 10 flags, how many different versions of the app are live at the same time?

Each flag doubles the number of possible combinations: 3 flags give 8, 10 flags give 1,024. Only about 200 users are active, so the live count stops near the number of users, and almost every user runs a combination nobody else has, and nobody tested. That is why finished rollouts should have their flag deleted: a flag that stays at 100% is still a branch someone has to reason about.

5. Staff first

Experiment 5 of 5
A buggy feature for 60 s · on for internal staff only (5% of traffic) vs on for 10% of all users
How many customers hit the bug in that minute?

Targeting lets the first users of a feature be the people who built it. Staff meet the bug, report it and the flag goes off before any customer sees it. A percentage rollout picks users at random, so customers are in the first group. In practice teams chain both: staff, then a few percent of customers, then everyone, watching errors at each step.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1What does "separate deploy from release" mean, and what does it buy you?
A good answer coversDeploying puts the new code on the servers; releasing decides who runs it. With a flag the code ships dark, and turning it on or off is a settings change, not a build. You can deploy on Tuesday, release to staff on Wednesday, to 10% on Thursday, and switch it off in seconds if it breaks, without a redeploy.
Q2Why hash the user id for a percentage rollout instead of picking randomly per request?
A good answer coversA random roll per request flips the same user between versions, which breaks their experience and your metrics. Hashing the user id (with the flag name as salt) gives each user a stable bucket, so they always see the same thing, and raising the percentage only adds users. Including the flag name means different flags don't all pick the same users.
Q3You flip a kill switch and some users still see the feature for a while. Why, and how would you shorten that?
A good answer coversEach server evaluates flags from a cached copy that refreshes on a timer, so servers keep serving the old setting until their next refresh. Shorten the refresh interval, use a flag service that pushes changes (streaming), and for kill switches make sure the client also re-evaluates rather than caching the decision for a whole session.
Q4Your team has 40 flags, many at 100% for months. What's the risk, and what would you do?
A good answer coversEvery flag is a branch in the code and a dimension in the test matrix. Old flags hide dead code, make bugs depend on flag combinations nobody tested, and a stray toggle can switch off something everyone relies on. Give each release flag an owner and an expiry, remove the flag and the old path once it's at 100%, and keep only long-lived operational flags (kill switches, limits) on purpose.
Q5Is a feature flag a replacement for a canary deploy or a rollback?
A good answer coversNo, they cover different risks. A flag only protects the code it wraps; a bad dependency upgrade, a config change or a broken migration in the same deploy isn't behind any flag. Canaries and rollbacks protect the deploy itself; flags protect the release of a feature. Most teams use both.
Q6Where should flag evaluation happen, and what happens if the flag service is down?
A good answer coversUsually in the app, from a locally cached copy, so the flag service isn't on the request path. Every flag needs a safe default for when no copy is available (usually off for new features), and servers should keep using their last good copy rather than failing when the service is unreachable.
