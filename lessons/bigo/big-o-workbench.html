Big-O WorkbenchBanco de trabajo: Big-O

Big-O describes how the work an algorithm does grows as its input grows. It ignores what one step costs and keeps how the number of steps scales: constant, logarithmic, linear, n log n, quadratic. This lesson races five real algorithms on the same data: watch them, predict what changes, then explain it back.La notación Big-O describe cómo crece el trabajo de un algoritmo cuando crece su entrada. Ignora cuánto cuesta un paso y se queda con cómo escala la cantidad de pasos: constante, logarítmica, lineal, n log n, cuadrática. Esta lección pone a competir cinco algoritmos reales sobre los mismos datos: míralos, predice qué cambia y después explícalo.

1. Double nDuplica n

Experiment 1 of 5Experimento 1 de 5
n goes from 1,000 to 2,000 · same kind of data, same five algorithmsn pasa de 1,000 a 2,000 · el mismo tipo de datos, los mismos cinco algoritmos
What happens to each lane's step count?¿Qué le pasa a la cuenta de pasos de cada carril?

Big-O describes how work grows as n grows. Doubling n adds one halving to a binary search, doubles a scan, slightly more than doubles a sort (its log n factor grows too), and quadruples anything that compares every pair. That growth, not the count at one size, decides whether code survives ten times more data. On the track it's the distance each post moves: on a log scale, doubling is the same short hop for O(n), twice that for O(n²).Big-O describe cómo crece el trabajo cuando crece n. Duplicar n le agrega una división a la mitad a una búsqueda binaria, duplica un recorrido, poco más que duplica un ordenamiento (su factor log n también crece) y cuadruplica todo lo que compara cada par. Ese crecimiento, no la cuenta en un solo tamaño, decide si un código aguanta diez veces más datos. En la pista es la distancia que se mueve cada poste: en escala logarítmica, duplicar es el mismo salto corto para O(n) y el doble de largo para O(n²).

2. Sorting 16 itemsOrdenar 16 elementos

Experiment 2 of 5Experimento 2 de 5
Insertion sort, O(n²) with almost no overhead, vs merge sort, O(n log n), which copies halves and makes a call at every level · each comparison and move costs 1, each merge-sort call 12 more · 8 seeded shufflesInsertion sort, O(n²) casi sin costo extra, contra merge sort, O(n log n), que copia mitades y hace una llamada en cada nivel · cada comparación y movimiento cuesta 1, cada llamada de merge sort 12 más · 8 mezclas con semilla fija
At n = 16, which one does less work?Con n = 16, ¿cuál hace menos trabajo?

Big-O drops constants and small terms, and at small n those are most of the cost. Insertion sort's inner loop is one compare and one move; merge sort pays to split, copy and call at every level. Past the crossover the growth rate takes over and merge sort wins by more and more. Real sorts combine both: Python's Timsort sorts short runs (32 to 64 items) with insertion sort before merging them. Where the crossover sits depends on the machine and the language, so libraries measure it rather than derive it.Big-O descarta las constantes y los términos pequeños, y con n pequeño esos son casi todo el costo. El bucle interno de insertion sort es una comparación y un movimiento; merge sort paga por dividir, copiar y llamar en cada nivel. Pasado el punto de cruce, el ritmo de crecimiento manda y merge sort gana por cada vez más. Los ordenamientos reales combinan los dos: Timsort, el de Python, ordena tramos cortos (de 32 a 64 elementos) con insertion sort antes de mezclarlos. Dónde cae el cruce depende de la máquina y del lenguaje, así que las bibliotecas lo miden en vez de deducirlo.

3. A loop hiding inside .includes()Un bucle escondido dentro de .includes()

Experiment 3 of 5Experimento 3 de 5
For each of 10,000 orders, check whether its customer is on a list of 10,000 · list.includes(id), which scans the array, vs a Set built oncePara cada uno de 10,000 pedidos, revisa si su cliente está en una lista de 10,000 · list.includes(id), que recorre el array, contra un Set construido una vez
How much more work does the array version do?¿Cuánto más trabajo hace la versión con el array?

includes, indexOf and find scan the array, so calling one inside a loop over n items is a loop inside a loop: about n × n/2 steps when values are found, n × n when they aren't. A Set costs n to build, then each lookup is about one step (a hash and a compare or two). The code looks just as simple; the growth isn't. Other common hidden loops: removing from the front of an array inside a loop, building a string with += in languages where strings are copied, and one database query per row (the N+1 lesson).includes, indexOf y find recorren el array, así que llamar a uno dentro de un bucle sobre n elementos es un bucle dentro de otro: unos n × n/2 pasos cuando los valores están, n × n cuando no. Un Set cuesta n al construirse y después cada búsqueda es más o menos un paso (un hash y una o dos comparaciones). El código se ve igual de simple; el crecimiento no. Otros bucles escondidos comunes: quitar del inicio de un array dentro de un bucle, armar un string con += en lenguajes donde los strings se copian, y una consulta a la base de datos por fila (la lección de N+1).

4. Sort once, or scan every time?¿Ordenar una vez o recorrer cada vez?

Experiment 4 of 5Experimento 4 de 5
10,000 unsorted items · q lookups, about half for values that aren't there · plan A: scan for each one · plan B: merge sort once, then binary search each one10,000 elementos sin ordenar · q búsquedas, cerca de la mitad de valores que no están · plan A: recorrer para cada una · plan B: ordenar una vez con merge sort y después búsqueda binaria para cada una
After how many lookups does sorting first pay off?¿Después de cuántas búsquedas conviene haber ordenado primero?

For one lookup, scanning wins: the sort costs about n log n before you've found anything. But each scan costs up to n while each binary search costs about log n, so the sort pays for itself after roughly (n log n) ÷ n, about log n lookups. That's amortising a cost over later work, and it's why databases keep indexes (sorted structures paid for on every write) and why you build a Set or a Map before a loop, not inside it.Para una sola búsqueda, recorrer gana: el ordenamiento cuesta unos n log n antes de encontrar nada. Pero cada recorrido cuesta hasta n y cada búsqueda binaria unos log n, así que ordenar se paga solo después de más o menos (n log n) ÷ n, unas log n búsquedas. Eso es amortizar un costo sobre el trabajo que viene, y es por qué las bases de datos mantienen índices (estructuras ordenadas que se pagan en cada escritura) y por qué construyes un Set o un Map antes de un bucle, no dentro de él.

5. Insertion sort on data that's already sortedInsertion sort con datos ya ordenados

Experiment 5 of 5Experimento 5 de 5
1,000 items · already sorted, shuffled, then reversed · the same insertion sort · steps are comparisons plus moves1,000 elementos · ya ordenados, mezclados y después invertidos · el mismo insertion sort · los pasos son comparaciones más movimientos
How many steps on the already-sorted input?¿Cuántos pasos con la entrada ya ordenada?

Big-O is usually quoted for the worst case, but the cost depends on the input's shape. Insertion sort shifts nothing when items are already in order, so it's linear on sorted or nearly sorted data, quadratic on shuffled data and worst on reversed data. Timsort leans on this by finding runs that are already in order. The flip side: a quicksort that always picks the first item as its pivot is fast on random data and quadratic on sorted data, which real inputs often are.Big-O se suele dar para el peor caso, pero el costo depende de la forma de la entrada. Insertion sort no mueve nada cuando los elementos ya están en orden, así que es lineal con datos ordenados o casi ordenados, cuadrático con datos mezclados y peor todavía con datos invertidos. Timsort se apoya en esto buscando tramos que ya están en orden. La otra cara: un quicksort que siempre elige el primer elemento como pivote es rápido con datos aleatorios y cuadrático con datos ordenados, que es como suelen llegar los datos reales.

Explain it backExplícalo

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.Responde en voz alta o por escrito antes de abrir cada una. Funcionan bien en pareja: una persona explica y la otra pregunta "¿por qué?" dos veces.

Q1P1What does "this function is O(n)" promise, and what does it leave out?¿Qué promete "esta función es O(n)" y qué deja afuera?
A good answer coversUna buena respuesta cubreThat its work grows at most in proportion to n once n is large. It leaves out the constant (a step might be a nanosecond or a network call), smaller terms, how it behaves at small n, and which input it describes (usually the worst case).Que su trabajo crece como mucho en proporción a n cuando n es grande. Deja afuera la constante (un paso puede ser un nanosegundo o una llamada de red), los términos más pequeños, cómo se comporta con n pequeño y qué entrada describe (normalmente el peor caso).
Q2P2An endpoint takes 200 ms with 1,000 rows. Estimate it at 10,000 rows if its main loop is O(n), O(n log n) or O(n²).Un endpoint tarda 200 ms con 1,000 filas. Estima cuánto tarda con 10,000 filas si su bucle principal es O(n), O(n log n) u O(n²).
A good answer coversUna buena respuesta cubreO(n): about 2 s. O(n log n): a little more, about 2.7 s, since log n grows from about 10 to about 13. O(n²): about 20 s, a hundred times longer. This assumes the loop dominates; fixed costs like the connection and serialising the response don't grow with n.O(n): unos 2 s. O(n log n): un poco más, unos 2.7 s, porque log n crece de unos 10 a unos 13. O(n²): unos 20 s, cien veces más. Esto supone que el bucle domina; los costos fijos, como la conexión y serializar la respuesta, no crecen con n.
Q3P3Why do real sort functions switch to insertion sort, an O(n²) algorithm, for small pieces?¿Por qué las funciones de ordenamiento reales pasan a insertion sort, un algoritmo O(n²), para los pedazos pequeños?
A good answer coversUna buena respuesta cubreAt small n the constant factors dominate: insertion sort is a tight compare-and-move loop with no allocation or recursion, so it does less real work than an O(n log n) sort until n reaches a few dozen. It's also linear on data that's almost sorted. Libraries pick the threshold by measuring.Con n pequeño dominan las constantes: insertion sort es un bucle ajustado de comparar y mover, sin reservar memoria ni recursión, así que hace menos trabajo real que un ordenamiento O(n log n) hasta que n llega a unas pocas docenas. También es lineal con datos casi ordenados. Las bibliotecas eligen el umbral midiendo.
Q4P4Name three ways a quadratic loop hides in ordinary-looking code.Nombra tres formas en que un bucle cuadrático se esconde en código que se ve normal.
A good answer coversUna buena respuesta cubreincludes, indexOf or find inside a loop; removing or inserting at the front of an array (shift, unshift, splice) inside a loop; building a string with += where strings are copied; nested filter or map over two lists; one database query per row (N+1).includes, indexOf o find dentro de un bucle; quitar o insertar al inicio de un array (shift, unshift, splice) dentro de un bucle; armar un string con += donde los strings se copian; filter o map anidados sobre dos listas; una consulta a la base de datos por fila (N+1).
Q5P5Why is O(log n) almost as good as O(1) in practice, and when is O(1) not really cheap?¿Por qué O(log n) es casi tan bueno como O(1) en la práctica, y cuándo O(1) no es realmente barato?
A good answer coversUna buena respuesta cubreA binary search over a billion items takes about 30 steps, and doubling n adds one. A hash lookup is O(1) on average but each step is a hash plus a compare, collisions or a bad hash can make it slow, a resize copies everything, and a memory read that misses the cache can cost a hundred times more than one that hits.Una búsqueda binaria sobre mil millones de elementos toma unos 30 pasos, y duplicar n agrega uno. Una búsqueda en un hash es O(1) en promedio, pero cada paso es un hash más una comparación, las colisiones o un mal hash pueden volverla lenta, un redimensionamiento copia todo, y una lectura de memoria que no está en la caché puede costar cien veces más que una que sí.
Q6P6When is it worth sorting or building an index before you search?¿Cuándo vale la pena ordenar o construir un índice antes de buscar?
A good answer coversUna buena respuesta cubreWhen you'll search the same data many times. Building costs about n log n (or n for a hash set) once; each later lookup then costs log n (or about 1) instead of n, so the build pays off after roughly log n lookups. For a single lookup, just scan.Cuando vas a buscar en los mismos datos muchas veces. Construirlo cuesta unos n log n (o n para un hash set) una vez; después cada búsqueda cuesta log n (o más o menos 1) en vez de n, así que la construcción se paga después de unas log n búsquedas. Para una sola búsqueda, simplemente recorre.
