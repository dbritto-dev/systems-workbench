Rolling Deploy Workbench

A rolling deploy replaces a service one piece at a time, so it never has to stop. This lesson builds the idea three ways: watch a crane swap modules in a running yard, predict what each setting breaks, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results are averaged over eight simulated rollouts of the same yard: six bays, 6 s warm-up, 2.4 s per crane move.

1. Take more bays out at once

Experiment 1 of 5
maxUnavailable 1 → 3 · busy traffic (2 requests/s, six bays serve 3/s)
Half the bays may now be out at the same time. What happens?

maxUnavailable is how much capacity the rollout may take away. Three bays out leaves 1.5 requests/s of capacity for 2 requests/s of traffic, so queues grow until new bays come up. The rollout is faster because three modules warm up at the same time, but warm-up still sets the pace, so it is not three times faster.

2. Add before you remove

Experiment 2 of 5
maxUnavailable 1, maxSurge 0 → maxUnavailable 0, maxSurge 1 · busy traffic
Now a new bay is added before any old one is taken out. What does that cost?

With maxSurge the rollout adds a new bay in a spare position first and only removes an old one once the new one is ready, so capacity never drops below six bays. The price is the extra bay: your cluster needs room for seven while it runs. It is not slower, because each step still waits for exactly one warm-up.

3. No readiness probe

Experiment 3 of 5
Readiness probe on → off · a new bay's flag rises as soon as it is installed
The new version is fine, but every module needs 6 s to warm up. Without the probe…

The flag is the only thing the distributor looks at. Without a probe it rises the moment the module is in place, so requests go to a bay that cannot answer yet. Worse, a new bay has an empty queue, so a least-busy distributor sends it more than its share. The rollout also looks twice as fast, because nothing waits for warm-up: that speed is the bug.

4. A broken version

Experiment 4 of 5
Next version: broken · it starts, but never passes its health check
With the readiness probe on, how far does the rollout get?

The rollout only removes another old bay when enough bays are ready. A new bay that never becomes ready keeps it waiting forever, so the damage stays at one bay. It does not roll back: in Kubernetes the deployment is marked as failed after progressDeadlineSeconds and someone (or a pipeline) runs kubectl rollout undo. Without the probe, nothing stops it.

5. Two versions at once

Experiment 5 of 5
Next version saves user data in a new format that the old version cannot read
During the rollout, old and new bays both serve. What do users see?

A rolling deploy always has a window where both versions serve, and a user can bounce between them from one request to the next. Anything one version writes, the other must be able to read. Ship format changes in steps: first a version that reads both formats, then one that writes the new one (expand, then contract).

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1maxUnavailable and maxSurge both make a rollout faster. What does each one cost?
A good answer coversmaxUnavailable spends capacity: bays are taken out before replacements are ready, so the remaining bays carry more load and waits grow. maxSurge spends resources: extra bays run alongside the old ones, so you need room in the cluster. With maxUnavailable 0 and maxSurge 1 you never drop below full capacity.
Q2Why does a readiness probe make a broken rollout stop by itself, and what does it not do for you?
A good answer coversThe rollout only removes another old bay when enough bays are ready. A new bay that never becomes ready blocks that, so only one bay is lost and the old ones keep serving. It does not roll back: the deployment just stops progressing (Kubernetes marks it failed after progressDeadlineSeconds), and someone has to run a rollback.
Q3Without the probe, the rollout finished in half the time. Why is that number misleading?
A good answer coversIt finished faster because nothing waited for warm-up: each flag rose the moment the module was in place. The time saved was paid for with failed requests sent to bays that could not answer yet.
Q4A new version renames a field in the data it stores. How do you ship it with a rolling deploy?
A good answer coversIn steps, because old and new versions serve side by side during every rollout. First deploy a version that can read both the old and the new field but still writes the old one; once that is everywhere, deploy the version that writes the new one; later remove the old field (expand, then contract).
Q5A brand-new bay has an empty queue. Why can that hurt right after it becomes ready, and what helps?
A good answer coversA least-busy distributor sends it a burst of traffic, while it may still be cold (caches empty, JIT not warmed). A readiness probe that only passes when it can really serve, a short warm-up delay, or slow-start in the load balancer all help.
Q6When would you choose blue-green or canary instead of a rolling deploy?
A good answer coversBlue-green when you cannot have two versions serving at once or want an instant, complete rollback. Canary when you want to try the new version on a small share of real traffic and judge it by metrics before going further. Rolling is the cheap default when versions are compatible and gradual replacement is fine.
