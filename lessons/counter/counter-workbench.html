Systems lesson 21 · Distributed counters

Counter Workbench

Counting sounds trivial until several machines count at once. This lesson builds a grow-only counter three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, averaged over eight seeded runs.

1. Read, add one, write it back

Experiment 1 of 5
One shared key · each add reads the count, adds 1 and writes the result · 3 branches, 0.3 adds/s each, for 60 s
Every add does its read and its write successfully. What share of the adds end up in the register?

Two branches that read the same value both write value + 1, and one add disappears. With half a second between a read and its write, overlaps are common even at a gentle rate, and nothing reports an error: every write succeeds. This is a lost update, the classic read-modify-write race, now across machines.

2. Compare-and-swap

Experiment 2 of 5
The write becomes "set to v + 1 only if it is still v" · on failure, read again and retry · traffic 0.1 → 0.6 adds/s per branch
The count is now exact at both rates. What changes as traffic grows?

The stamp only accepts a write if nobody changed the value since this branch read it. With more branches adding at once, more writes are rejected and must read again. The count stays exact, but every retry costs two more courier trips, and at high traffic adds queue up behind each other on the single key.

3. One slot per branch

Experiment 3 of 5
Each branch writes only its own slot (its own count) · the total is the sum of all slots · 0.6 adds/s per branch, where compare-and-swap struggled
How many adds are lost or retried now?

A branch only ever writes the slot it owns, so there is nothing to race on: no lost updates, no compare-and-swap, no retries. Reading adds up every slot. This is a grow-only counter (G-counter), one of the simplest CRDTs: replicas that can always merge (take each slot's highest value) and agree.

4. Branch C is cut off

Experiment 4 of 5
One slot per branch · C's track is cut for 15 s, then healed · adds stop when it heals
What happens to the count while C is cut off, and after?

C keeps counting its own adds in its own slot, but its reads can't reach the register and its writes wait at the barrier. So C misses A and B's adds, and A and B miss C's. When the track heals, C's queued writes land, every branch reads every slot, and they all agree on the exact total. Always available, eventually consistent.

5. Reading right after an add

Experiment 5 of 5
Compare-and-swap · B adds 1 and gets its acknowledgement · at that moment A and B each read the count · 20 tries
Does A's read include B's add?

The register is only sequentially consistent: everyone sees the writes in the same order, and each branch never goes backwards from what it has already seen, but a read may be served from a state a moment old. B has seen its own write, so B's read includes it. A hasn't, so A can lag. If a user must see their own update, read through the branch that made it, or use a linearizable store.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1Two services each read a counter, add one and write it back. Both succeed, yet the counter only went up by one. Why, and why did nothing report an error?
A good answer coversBoth read the same old value, so both wrote old + 1; the second write replaced the first. Each request was valid on its own, so no error is raised. The fix is an atomic operation: compare-and-swap, an atomic increment in the store, or a design where writers never share a key.
Q2How does compare-and-swap prevent the lost update, and what does it cost?
A good answer coversThe write only succeeds if the value is still what you read; otherwise you re-read and try again. Nothing is lost, but under contention many attempts fail, each costing round trips, and throughput on that one key is capped by how fast read-then-write cycles can complete.
Q3Explain a G-counter in one minute.
A good answer coversEach node keeps its own count in its own slot and only ever increments it. The value is the sum of all slots. Two copies merge by taking the maximum of each slot, so merges never conflict and every replica ends up with the same total, no matter the order messages arrive in.
Q4During a network partition, what does a G-counter give up, and what does it keep?
A good answer coversIt gives up up-to-date reads: each side misses the other side's increments. It keeps availability (adds still succeed on both sides) and correctness after healing: no increment is lost or double counted, and everyone converges on the exact total.
Q5Your store is sequentially consistent. A user clicks "like", then reloads and sees the old count. What happened, and how would you fix it?
A good answer coversThe reload was served from a replica or state that hadn't caught up yet. Sequential consistency only guarantees order, not recency. Fixes: read from the node that took the write (session stickiness), wait for or require a version at least as new as the write, or use a linearizable read for that path.
Q6When would you choose a single atomic counter in a database over a CRDT counter?
A good answer coversWhen reads must be exact and current (balances, stock that must not oversell) and the write rate on that key is moderate. CRDT counters win for high-volume, approximate-is-fine-for-a-moment counts (likes, views, metrics) and when writes must keep working during partitions.
