Systems lesson 25 · Idempotency keys

Idempotency Workbench

When a reply goes missing, the client can't tell whether its request worked, so it sends it again. An idempotency key lets the server recognise the retry and answer it with the result it already produced, instead of doing the work twice. This lesson builds that on a payment counter: watch it, predict what breaks it, then explain it back.

01

The machine

Four customers pay at a counter over lanes that sometimes lose the reply. Watch the till: card charges should match orders paid. With keys on, retries are answered from the rack of stored receipts; switch keys off, make the customers impatient or let keys expire, and watch charges run ahead of orders.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, averaged over eight seeded three-minute runs.

1. Lost replies, no keys

Experiment 1 of 5
Keys off · 1 reply in 10 is lost on the way back · a customer who hears nothing in 5 s pays again · 4 customers, 3 minutes
The counter charges correctly every time it receives a slip. Out of roughly 120 orders, how many end up charged twice?

A lost reply looks exactly like a lost request from the customer's side: no answer. So the customer pays again, and the counter, which has no memory of the first slip, charges again. Every lost reply after a successful charge becomes a double charge. Nothing failed on the server; the duplicate was created by a correct retry.

2. Remember the result

Experiment 2 of 5
Every order carries a key · the counter files key → receipt after charging · a slip whose key is on file gets the stored receipt back · same 10% loss
What happens to the retries now?

The retry carries the same key, finds the receipt in the rack and gets the original answer back, with no second charge. From the customer's side it looks exactly like the first reply arriving late, which is the point: an idempotent operation can be repeated safely, so retries become harmless.

3. An impatient customer

Experiment 3 of 5
Customers wait only 1 s before paying again · charging takes 1.2–2.4 s · no replies lost · the key is filed only once the charge is done
Keys are on and no reply is ever lost. How many orders are charged twice?

The retry arrives while the first charge is still running, and the rack has nothing filed for that key yet, so the counter charges again. Checking a key and filing it later is a race. The fix is to claim the key before doing the work: an in-progress marker written atomically (a unique insert), so a second slip with the same key is told "still in progress" (409) and tries again later, when the receipt is on file.

4. Keys that expire

Experiment 4 of 5
Key lifetime 1 day → 8 s · 3 replies in 10 lost · retries back off 1, 2, 4 s, so a third try comes about 14 s after the first
With the in-progress marker on, does a short key lifetime change anything?

Once a key is forgotten, a retry with that key is a brand-new request, so it is charged. A key must be kept for longer than the longest time a client may still retry the same operation (including retries after an app restart or a queue redelivery). Payment APIs keep keys for about 24 hours for this reason.

5. Same key, different amount

Experiment 5 of 5
A buggy client recalculates the total (+$5) on half of its retries but reuses the order's key · 3 replies in 10 lost · keys on
What should the counter do with a retry whose key is on file but whose amount differs?

A key names one specific operation. If the request behind it changed, either the client has a bug or two different operations share a key; replaying the old receipt would tell the client the new amount was charged when it wasn't, and charging would double-charge. So the server keeps a fingerprint of the original request and rejects a mismatch loudly (422), which surfaces the client bug.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1The payment service charged the card once for every request it received, yet a customer was charged twice. How?
A good answer coversThe first charge succeeded but its reply was lost (or arrived after the client's timeout). The client can't tell that apart from a failed request, so it retried, and the server, with no memory of the first request, treated the retry as a new payment. Retries are correct behaviour; the server must make them safe.
Q2What should the server store for each idempotency key, and why the whole response rather than just "seen"?
A good answer coversThe response it sent (status and body) plus a fingerprint of the request. A retry must get the same answer the first request got, including the charge ID or the error, so the client can carry on as if the first reply had arrived. "Seen" alone would leave the server unable to answer the retry.
Q3Why is "look up the key, charge, then save the key" not enough?
A good answer coversTwo requests with the same key can arrive close together; both look up, both find nothing, both charge. The key must be claimed before the work starts, atomically: insert an in-progress row with a unique constraint, and answer a concurrent duplicate with 409 (or make it wait) until the first finishes and its response is stored.
Q4How long should keys be kept?
A good answer coversLonger than any client could still retry the same operation: across backoff schedules, app restarts, queued retries and message redeliveries. A day is common for payment APIs. Too short and late retries become duplicates; forever is unnecessary storage.
Q5Who generates the key, and how should keys be scoped?
A good answer coversThe client generates one key per logical operation (for example a UUID created when the user presses Pay) and reuses it for every retry of that operation, never for a different one. The server scopes keys per account or API client, so two clients that pick the same key can't see each other's results.
Q6Which operations need idempotency keys, and where else does the same idea show up?
A good answer coversAnything that isn't naturally idempotent: creating payments, orders, emails, transfers. PUT and DELETE that set a final state usually are idempotent already. The same idea appears in message consumers (dedupe by message ID under at-least-once delivery), webhooks, and the outbox pattern's relay.
