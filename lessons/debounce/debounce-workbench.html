Systems lesson 31 · Debounce

Debounce Workbench

A debounce waits until events stop for a moment and then acts once. Every new event restarts the wait, so a burst of keystrokes becomes one request. This lesson turns it into an elevator that leaves only when nobody new has arrived: watch it, predict what breaks it, then explain it back.

01

The machine

Every keystroke sends a passenger to the elevator. The door timer over the car restarts with each one; when it runs out, the whole group goes up to the server as one request. Turn debounce off and every passenger climbs the stairs alone. Change the wait, hold a key down, double-click, or type in the box yourself.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, averaged over six seeded runs of two minutes each.

1. Debounce the search box

Experiment 1 of 5
Search-as-you-type · every keystroke used to send a request · now: wait until 300 ms with no key, then send once
Someone types a search of about 12 characters, pausing briefly between words. How many requests does one search send now?

Each key restarts the 300 ms timer, so a request only leaves when the typist pauses for longer than that. Keys come about 170 ms apart inside a word, so a word's keys ride together; the short think between words is often longer than 300 ms, so a search sends one request per pause plus the final one. Fewer requests, not a guaranteed one.

2. Choose the wait

Experiment 2 of 5
Same typing · the debounce wait 100 ms → 300 ms → 1 s · a steady server that answers in about 0.2 s
What does each wait give you?

A wait only merges keys that arrive closer together than the wait. Typing gaps are longer than 100 ms, so almost every key still gets its own request. A long wait merges whole searches, but every search now pays that wait before the server even hears about it. Most search boxes land between 200 and 400 ms.

3. A key held down

Experiment 3 of 5
An event every 50 ms for 5 s (a held key, a scroll, a window resize), then 2 s of quiet · debounce 300 ms
When does the first request go out?

Every event restarts the timer, and the events never pause for 300 ms, so the door never closes: nothing is sent until the stream stops. That is starvation. A maximum wait fixes it: with maxWait 1 s the door closes at least once a second, whatever keeps arriving. If you want a steady beat during the stream, that is throttling, not debouncing.

4. A double click on Submit

Experiment 4 of 5
An impatient user double-clicks the order button, the clicks about 160 ms apart · no debounce, trailing 300 ms, or leading 300 ms
Which setting sends exactly one order, and sends it immediately?

Without debounce both clicks become orders. Trailing debounce sends one order, but only 300 ms after the last click, so the button feels slow. Leading debounce sends on the first click and ignores everything until 300 ms of quiet: one order, at once. The server should still refuse duplicates (an idempotency key), because the client cannot catch every double submit.

5. Slow answers arrive late

Experiment 5 of 5
Typing with a server that is usually quick but takes 1 to 2.5 s for one request in six · no debounce, debounce 300 ms, then debounce plus cancelling the older request
With a 300 ms debounce, can the screen still show results for an older search after a newer one?

Debounce decides when requests leave, not when answers come back. If an early request hits the slow path and a later one does not, the early answer lands last and replaces the right one on the screen. Fewer requests means fewer chances, not none. Abort the previous request (AbortController), or tag each request and ignore any answer older than the newest one shown.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1In one sentence, what does a debounce do, and how is it different from a throttle?
A good answer coversA debounce waits until events stop for a set time and then acts once, every new event restarting the wait. A throttle acts at most once per interval while events keep coming. Debounce answers "when they're done", throttle answers "at a steady pace".
Q2Why did a 100 ms debounce barely reduce the requests from typing?
A good answer coversIt only merges events that arrive within 100 ms of each other. Most people type with gaps longer than that, so nearly every keystroke still finds the timer expired and sends its own request. The wait has to be longer than the gap you want to merge.
Q3Search box: trailing. Submit button: leading. Why the different edges?
A good answer coversA search should run on the final text, after typing stops, so it waits for the trailing edge. A submit should react to the first click at once and ignore the accidental second one, so it fires on the leading edge and stays closed until things go quiet.
Q4A debounced scroll handler never runs while the user keeps scrolling. Why, and what are two fixes?
A good answer coversEach scroll event restarts the timer and they never pause long enough for it to run out. Add a maximum wait so it fires at least every N ms, or use a throttle when you want regular updates during the stream.
Q5Your debounced search still sometimes shows results for an earlier query. Why doesn't debounce prevent that, and what does?
A good answer coversDebounce only spaces out when requests leave; answers can still come back in any order. Cancel the in-flight request when you send a new one (AbortController), or remember the latest request id and drop any answer that is older.
Q6In React, a teammate writes const onChange = debounce(search, 300) inside the component body, and it doesn't debounce at all. What happened, and how do you fix it?
A good answer coversEvery render creates a new debounced function with its own empty timer, so each keystroke goes to a fresh one. Create it once (useMemo or useRef, or a useDebouncedCallback hook), keep the latest search in a ref if it changes, and cancel the pending call when the component unmounts.
