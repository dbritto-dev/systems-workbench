Systems lesson 07 · Consistent hashing

Hash Ring Workbench

When data is split across nodes, every key needs a home, and adding or losing a node should move as few keys as possible. This lesson compares two ways of choosing the home, hash mod n and a hash ring, three ways: watch a machine do it, predict what each change does, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results use the machine's own model with 1,000 keys; ring results are averaged over 200 clusters, because they depend on where the markers happen to land.

1. Add a node, modulo style

Experiment 1 of 5
bin = hash mod n · nodes 4 → 5
One node joins a cluster of four. What share of the 1,000 keys has to move to a different node?

A key stays put only if hash mod 4 and hash mod 5 happen to agree, and that is true for just 4 numbers in every 20. Everything else is reshuffled, between every pair of nodes, not just toward the new one. On a cache cluster that means four in five reads suddenly miss.

2. Add a node, on a ring

Experiment 2 of 5
Hash ring, 1 marker per node · nodes 4 → 5
Same change, but keys go to the next marker clockwise. Which keys move?

The new node's marker lands somewhere on the ring and claims only the arc just before it. Those keys used to slide on to the next marker clockwise, so they all come from that one neighbour. Every other key still reaches the same marker as before.

3. Is the ring fair?

Experiment 3 of 5
Hash ring, 5 nodes · 1 marker per node
Five nodes, one marker each, placed by hashing. How much does the busiest node get compared with a fair fifth?

Five random points cut the ring into five arcs of very different lengths, and each node owns one arc. Give every node many markers (virtual nodes) and each node owns many small arcs, which average out: with 100 markers the busiest node is close to fair.

4. A node fails

Experiment 4 of 5
Hash ring, 5 nodes, 1 marker per node · node C fails
C's keys must go somewhere. Where do they go?

With one marker per node, C's whole arc now slides on to the next marker, so one neighbour takes all of C's work on top of its own, often the moment it can least afford it. With many markers C's arcs are scattered round the ring and their next markers belong to different nodes, so the work spreads over everyone.

5. One very popular key

Experiment 5 of 5
Hash ring, 100 markers per node · key 7 gets 30% of all requests
Does consistent hashing spread a hot key's traffic?

Consistent hashing decides where each key lives, and a key lives on one node. The node that owns key 7 carries 30% of the traffic plus its own share of the rest, however many nodes you add. Hot keys need a different tool: replicate that key to several nodes, cache it closer to the callers, or split it into sub-keys.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1Why does hash mod n move almost every key when n changes by one?
A good answer coversA key keeps its node only when hash mod n and hash mod (n + 1) agree, which happens for about 1 in n + 1 keys. So going from 4 to 5 nodes keeps about 1 in 5 and moves the other 80%, between all pairs of nodes, not just onto the new one.
Q2On a ring, exactly which keys move when a node is added, and where do they come from?
A good answer coversOnly the keys in the arc between the new marker and the previous marker counter-clockwise. They used to slide on to the next marker clockwise, so they all come from that node. Every other key reaches the same marker as before.
Q3What problem do virtual nodes solve? Name two.
A good answer coversBalance: a few random markers cut the ring into very uneven arcs (the busiest node had about 2.3× its fair share with one marker); many markers per node average out. Failure: with one marker a dead node's whole arc lands on one neighbour; with many, its arcs spread over all survivors. They also let a bigger machine take more markers.
Q4You run a cache cluster in front of a database and add a node. Compare modulo and a ring.
A good answer coversWith modulo about 80% of keys now map to a different node, so 80% of reads miss at once and hit the database: the same stampede as emptying the cache. With a ring only about 1 in n + 1 keys move, so the miss spike is small and lands on the keys of one neighbour.
Q5One key gets 30% of all requests and its node is overloaded. What would you do?
A good answer coversConsistent hashing won't help: a key lives on one node. Replicate the hot key to several nodes and read from any of them, cache it closer to the callers (in-process), or split it into sub-keys (key#1…key#n) and combine the results. Also find out why one key is that hot.
Q6Where have you met consistent hashing in real systems?
A good answer coversMemcached and Redis client-side sharding, Cassandra and DynamoDB partitioning, load balancers that keep a user on the same backend (Envoy ring hash, Maglev), and CDNs choosing which edge server holds an object. A good answer also notes that moving a key means moving its data, which is why moving fewer keys matters.
