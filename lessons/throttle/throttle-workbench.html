Systems lesson 32 · Throttle

Throttle Workbench

Some events arrive far faster than you need to act on them: a scroll or a pointer fires 60 to 120 times a second. A throttle lets the handler run at most once per interval, keeps the newest event and drops the rest. This lesson builds one as a machine: watch it, predict what changes it, then explain it back.

The machine

Event balls roll from the hopper to a gate held by a metronome. One swing is one interval: the first ball goes straight through, the newest one waits on the flap, the rest fall into the bin, and the waiting ball goes through when the swing ends. Watch the rail in front: the frame (what the screen shows) chases the figure (where the user is). Try Leading only, then Debounce, then Clicks.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, averaged over eight seeded runs of 20 seconds of input.

1. Throttle a scroll handler

Experiment 1 of 5
A scroll fires 120 events a second · the handler takes 6 ms · no gate → throttle, 100 ms
While the user is scrolling, how often does the handler run with the throttle?

A throttle runs the handler at most once per interval while events keep coming, and drops the events in between. For a scroll position that is exactly right: only the newest position matters, and a screen that updates ten times a second still feels live. The work drops by an order of magnitude and stops competing with scrolling itself.

2. Leading edge only

Experiment 2 of 5
Throttle 100 ms · run on the leading edge only (no trailing call) · scroll in bursts, then stop
When the user stops scrolling, does the handler see the position they stopped at?

Leading-only acts on the first event of each window and drops the rest. The user's final position usually arrives mid-window, so it is dropped and nothing ever comes after it: the screen stays a few pixels behind where the user stopped. A trailing call keeps the newest event waiting and runs it when the window closes, so the final state always lands. Most libraries default to both edges for this reason.

3. Throttle or debounce a drag

Experiment 3 of 5
A steady 3 s drag at 60 events a second · throttle 100 ms → debounce 100 ms
How many updates does each give during the drag itself?

Debounce waits for a quiet gap: every new event winds its timer back, so during a continuous drag it never fires; it runs once, after the drag ends. That is right for a search box or saving a draft, and wrong for anything that should follow the pointer. Throttle fires on a steady beat during the burst, which is what live feedback needs.

4. Throttle the add-to-cart button

Experiment 4 of 5
Bursts of quick clicks, one every 130–220 ms · each click should add one item · throttle 500 ms
What happens to the cart?

A throttle is lossy by design: it keeps the newest event and drops the others. That is fine when only the latest value matters (a position, a size) and wrong when every event is its own piece of work. For clicks, handle each one (or make the operation idempotent and disable the button while a request is in flight); if you must space them out, queue them, which keeps every item but delivers the last one later and later.

5. Pick the interval

Experiment 5 of 5
Scrolling at 120 events a second · throttle interval 16 ms (one frame) → 100 ms → 500 ms
What does a longer interval buy, and what does it cost?

The interval is a dial between work and staleness. One call per frame (16 ms, or requestAnimationFrame) follows the input as closely as the screen can show it and still halves the work at 120 events a second. 100 ms cuts the work by ten but the screen can be a tenth of a second behind; 500 ms is cheap and visibly laggy. Pick the longest interval the user won't notice for that kind of feedback.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1In one sentence each: what does a throttle do, and what does a debounce do? Give one use for each.
A good answer coversA throttle runs the handler at most once per interval while events keep coming (scroll position, pointer tracking, progress updates). A debounce waits until events stop for a quiet interval and then runs once (search-as-you-type, autosave, reacting to the end of a resize).
Q2Why do throttles usually fire on both the leading and the trailing edge?
A good answer coversThe leading call gives instant feedback on the first event. The trailing call runs the newest event when the window closes, so the final state (where the user stopped) is always handled. Leading-only can leave the screen short of the final position; trailing-only adds a full interval of delay to the first response.
Q3A teammate throttled the "Pay" button to stop double charges. What's wrong with that, and what would you do?
A good answer coversA throttle drops events by design; it can still send two requests (one per window) and it silently swallows clicks the user meant. Disable the button while the request is in flight, and make the server call idempotent (an idempotency key) so a retry or double click can't charge twice.
Q4Why is requestAnimationFrame a good throttle for anything that draws?
A good answer coversIt runs once per frame, right before the browser paints, so work happens at most as often as the screen can show it, in step with rendering, and it pauses in background tabs. Keep the newest event in a variable and read it in the frame callback.
Q5How is this throttle different from the rate limiter in lesson 05?
A good answer coversA throttle lives in the caller and drops its own redundant work, keeping only the newest event. A rate limiter lives in the server and protects it from many callers: it refuses requests beyond a budget (HTTP 429), and the caller decides whether to retry. One is a courtesy to yourself, the other a defence against everyone.
Q6A dashboard receives 200 websocket messages a second and re-renders on each one; the tab freezes. How would you fix it without losing data?
A good answer coversSeparate receiving from drawing. Apply every message to an in-memory state (no data lost, nothing dropped), and throttle the render to the frame rate or ~10 times a second, always drawing the newest state. If the processing itself is heavy, batch the messages per frame.
