Systems lesson 11 · Database indexes

Index Workbench

An index is a second, sorted copy of a few columns that points back to the rows. It turns read-everything into look-it-up, and every write pays to keep it current. This lesson builds that idea three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Times come from the same cost model the machine runs on: a page of 100 books read in order costs 0.1 ms, a random page (a drawer level or a trip to a shelf) 0.4 ms, and a catalogue page holds 100 cards.

1. The table grows ten times

Experiment 1 of 5
10,000 → 100,000 rows · query ISBN = … · a catalogue on ISBN
A full scan gets about 10× slower. How much slower does the lookup through the ISBN catalogue get?

A catalogue is a tree: each drawer level narrows the search 100 ways. 10,000 cards need 2 levels and 100,000 need 3, so the lookup only grows by one drawer read. A scan has no shortcut: ten times the rows is ten times the pages.

2. A third catalogue

Experiment 2 of 5
100,000 rows · catalogues: ISBN → ISBN, author, author + year · adding books
You add two more catalogues so more queries are fast. What happens to adding a new book?

Every catalogue has to stay in sync with the shelves, so every insert walks down each catalogue and files a card, and every update to an indexed column moves one. Indexes are paid for on every write, whether or not anyone runs the queries they help.

3. The wrong end of a composite

Experiment 3 of 5
100,000 rows · one catalogue sorted by author, then year · query: year = 1969
The catalogue holds year on every card. What does the librarian do for a year-only search?

A composite index is sorted by its first column, then by the second within each first. Cards for 1969 are spread across every author, so there is no place to jump to. It helps queries on author, or author and year, but not year alone: the leftmost-prefix rule.

4. An index on a yes/no column

Experiment 4 of 5
100,000 rows · a catalogue on 'on loan' · 4 in 10 books are on loan
You ask for every book that is on loan. What does the planner choose?

An index pays one random trip to the shelf per matching row. When a large share of rows match, those trips cost far more than reading every page in order. Planners estimate this and pick the scan. Indexes pay off on selective filters: few rows out of many.

5. The title is on the card

Experiment 5 of 5
100,000 rows · titles by one author · catalogue on author → catalogue on author that also carries the title
How much does it help when the card already carries the title?

A plain index finds the 50 matching cards in a few drawer reads, then makes 50 trips to the shelves to read each title. When the card carries everything the query needs, the answer comes straight from the catalogue: an index-only scan. The price is a bigger catalogue that every write must also update.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1A table grows from 1 million to 100 million rows. Why does a lookup by primary key barely slow down while a full scan gets 100 times slower?
A good answer coversThe index is a B-tree: each level narrows the search by its fan-out (hundreds of keys per page), so the number of levels grows with the logarithm of the row count: maybe 3 levels become 4. A scan has to read every page, so its cost grows in direct proportion to the table.
Q2A write-heavy table already has eight indexes. What do you check before adding a ninth?
A good answer coversEvery insert, and every update that touches an indexed column, writes to every index, so writes slow down and the indexes take memory and disk. Check which queries the new index serves and how often, and whether an existing index could be extended instead. Find indexes nobody uses (in Postgres, idx_scan = 0 in pg_stat_user_indexes) and drop them.
Q3You have an index on (author, year). Which of these can use it: author = ?, author = ? AND year = ?, year = ?, author = ? ORDER BY year?
A good answer coversAll except year = ? alone. A composite index is sorted by its first column, then the next, so it serves any query that fixes a leftmost prefix, and it can also return rows already ordered by the next column. For year alone you need a separate index on year, or one that starts with year.
Q4The database ignores your index on status, which has four values. Why, and what would help?
A good answer coversEach value matches about a quarter of the table, and an index scan pays one random page read per matching row, so a sequential scan is cheaper and the planner picks it. If you only ever query a rare value (status = 'failed'), a partial index on just those rows is small and selective.
Q5What is a covering index, and what does it cost?
A good answer coversAn index that holds every column a query reads, so the database answers from the index without visiting the table (an index-only scan; in Postgres, INCLUDE adds non-key columns). It costs a larger index and more work on every write, so use it for hot queries, not by default.
Q6How do you check whether a query uses an index, and whether that is the right plan?
A good answer coversRun EXPLAIN (ANALYZE, BUFFERS) on it. Look for Seq Scan versus Index Scan or Index Only Scan, compare estimated and actual rows (bad estimates lead to bad plans), and look at the pages read. Then test with realistic data volumes: a plan on a small dev table can differ from production.
