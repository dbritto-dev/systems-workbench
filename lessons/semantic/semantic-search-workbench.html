Semantic Search Workbench

Semantic search finds text by meaning instead of by matching words. An embedding model turns every chunk of your documents into a vector, the query into another, and the chunks pointing the same way as the query come back first. This lesson lays a help centre out as a star map: watch a query find its neighbours, predict where meaning-matching fails, then explain it back.

02

Predict, then runPredice y ejecuta

Each experiment changes one thing. Choose what you expect before running it. Results come from the same embedding and the same search as the machine.

1. Same meaning, no shared words

Experiment 1 of 5Experimento 1 de 5
Query "my card was charged twice" · the help centre says "Seeing the same transaction two times on your statement is usually a pending authorisation."
The two sentences share no words. Where does that chunk rank?

"Charged" and "transaction" both land near payments, "twice" and "two times" both near duplicates, so the two vectors point the same way although no word repeats. That is what embeddings buy you over keyword search: paraphrases, synonyms and other people's vocabulary still match. The next results are other payment sentences, close in meaning but not about duplicates.

2. An exact error code

Experiment 2 of 5Experimento 2 de 5
Query "ERR-4012" · one sentence in the help centre explains exactly that code
Is the sentence about ERR-4012 the top result?

The model has no meaning for "4012": it is a rare token that only nudges the vector a little, while "ERR" points strongly at errors in general. So the query lands on "we show an error message with a short code" and other error text, and the one sentence that names the code also talks about webhooks and secrets, which pulls its vector away. Exact identifiers, SKUs, names and numbers are where keyword search (BM25) wins, and the reason hybrid search exists.

3. How big is a chunk?

Experiment 3 of 5Experimento 3 de 5
14 help-centre questions · top 3 chunks each · chunks of one sentence vs one section (heading and its sentences) vs a whole document
Which size hands the model a usable answer most cheaply?

A sentence alone can lose what it is about: "It usually takes 5 to 7 business days" is retrieved for the refund question, but without the sentence before it the model can't know what takes 5 to 7 days. Whole documents found every answer here only because each search handed over almost a third of this tiny help centre; real documents run to thousands of words, mix topics into one averaged vector, and don't fit many to a prompt. A section-sized chunk keeps its own context and stays specific.

4. Search the graph instead of everything

Experiment 4 of 5Experimento 4 de 5
3,000 chunks · 200 queries · top 10 · compare against every chunk vs a graph index searched with a beam of 10, 40 or 160
With a beam of 10, how many of the true 10 nearest does the graph find?

Comparing against every vector is exact but costs one comparison per chunk per query. A graph index (HNSW is the usual one) links each chunk to its near neighbours and hops toward the query, so it looks at a small fraction of the collection. It can stop in a good-but-not-best spot, so recall depends on how wide the search is: the beam (ef) trades comparisons for recall. Production systems tune it until recall is high enough, and measure it against an exact search.

5. Keep only results above 0.80

Experiment 5 of 5Experimento 5 de 5
A fixed cutoff · five queries: one word, a vague one, one the help centre can't answer, two specific questions
What does one fixed cutoff do across these queries?

A cosine similarity says which chunks are closest to this query, not how good the match is in absolute terms. Short queries, vague ones and long ones land at different heights, and a query about something the help centre doesn't cover still has nearest neighbours, sometimes close ones. Use the ranking (top k), then a reranker or a relative rule (within some distance of the best), and test cutoffs on real queries instead of trusting one number.

Explain it backExplícalo

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.Responde en voz alta o por escrito antes de abrir cada una. Funcionan bien en pareja: una persona explica y la otra pregunta "¿por qué?" dos veces.

Q1P1What does an embedding model turn a chunk into, and why does that make paraphrases match?
A good answer coversUna buena respuesta cubreA list of numbers, a vector, placed so that texts with similar meaning point in similar directions. The query is embedded the same way and the closest chunks by cosine similarity win, so "charged twice" and "duplicate payment" match without sharing a word.
Q2P2Your support search can't find the article for the order number a customer pasted. Why, and what do you add?
A good answer coversUna buena respuesta cubreIdentifiers, codes, names and numbers carry little meaning for an embedding model, so the query vector lands near generic text and the exact match ranks low. Keyword search (BM25) is built for exact tokens; run both and fuse the lists (hybrid search), or route identifier-looking queries to keyword search.
Q3P3How do you pick a chunk size?
A good answer coversUna buena respuesta cubreSmall enough that one chunk is about one thing (a big chunk's vector averages its topics and wastes the prompt), big enough to carry its own context (a lone sentence like "This cannot be undone" is useless). Sections or a few hundred tokens with headings kept, sometimes with overlap, is a common start; then measure on real questions.
Q4P4What does an approximate index like HNSW trade, and how would you know it's good enough?
A good answer coversUna buena respuesta cubreIt hops through a graph of near neighbours instead of comparing against every vector, so it is far faster but can miss some true nearest neighbours. The search width (ef) trades comparisons for recall. Measure recall@k against an exact search on a sample of real queries and raise ef until it is high enough.
Q5P5Why is a fixed similarity threshold like 0.8 a bad filter?
A good answer coversUna buena respuesta cubreCosine scores aren't calibrated: their range shifts with the model, the query's length and wording, and the collection. A good match for one query can score below a bad match for another, and an unanswerable query still has close-looking neighbours. Rank, then rerank or apply a relative cutoff, and check on real queries.
Q6P6Why doesn't the map on the table show the real distances?
A good answer coversUna buena respuesta cubreEach chunk is a point in a space with dozens of dimensions here and hundreds or thousands in real models. Squashing it onto a flat map keeps neighbourhoods roughly but bends distances, so two studs can look close and not be. The search always uses the real vectors; the map is only a picture.
