Systems lesson 28 · Cache stampede

Cache Stampede Workbench

A cache hides how much work the database would have to do. When a hot entry expires, every request that arrives before it is rebuilt misses at once and the database gets that hidden load in one burst. This lesson builds the herd and the fixes for it: watch a machine do it, predict what changes it, then explain it back.

01

The machine

A bakery with six trays in the case and an oven that bakes four orders at a time. Every tray was filled at the same moment, so they expire together. Watch customers line up, order tickets pile up on the rail and duplicate orders light up, then switch to one order per tray, serve stale, or add jitter.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, at larger scale, averaged over six seeded runs.

1. Everything expires at once

Experiment 1 of 5
A deploy fills 50 keys at the same moment, all with a 30 s TTL · 500 requests a second spread evenly · the oven has 8 shelves and bakes in 0.2 s, so it can take 40 orders a second
What happens around the 30 s mark?

Every key was cached at the same instant with the same TTL, so they all expire in the same instant. Each request that arrives before its key is baked again misses and sends its own order, and the oven can only take 40 a second. The queue makes every bake slower, which keeps keys empty longer, which lets more requests miss: the herd feeds itself.

2. Add ±20 % jitter

Experiment 2 of 5
Same deploy · every TTL is multiplied by a random factor between 0.8 and 1.2
What happens to the busiest second at the oven?

Jitter spreads the 50 expiries over 12 seconds instead of one instant. Each key's little herd is over before the next key expires, so the oven never queues and each refresh finishes in one bake. Jitter costs nothing and fixes the synchronised case, but a single very hot key still has its own herd.

3. One order per tray

Experiment 3 of 5
One hot key at 500 requests a second · 10 s TTL · 0.2 s bake · a miss now waits for the order already in the oven instead of sending its own (single-flight, request coalescing)
How many oven orders does each expiry cause now?

With every miss ordering, about 100 requests arrive during the bake and each sends a duplicate. Coalescing keeps one in-flight order per key; everyone else waits on it and is served by the same result. The oven sees one order per expiry, so the queue never forms and even the waiting customers are served sooner.

4. Serve the old loaf

Experiment 4 of 5
Same hot key, but a bake now takes 1 s · single-flight vs stale-while-revalidate (serve the expired loaf at once and refresh it with one background order)
With single-flight, about 500 customers wait up to a second at every expiry. With stale-while-revalidate…

Single-flight removes the duplicate work but not the wait: everyone who arrives during the bake waits for it. Stale-while-revalidate keeps serving the old value while one background order refreshes it, so the expiry becomes invisible to users. The price is freshness: for one bake's time, people see data slightly past its TTL, which is fine for a product page and not for a balance.

5. A slower oven

Experiment 5 of 5
One hot key at 200 requests a second · every miss orders · bake time 0.2 s → 1 s (five times slower)
What happens to the longest wait at an expiry?

A slower bake keeps the key empty five times longer, so five times as many requests miss, and they all land on the same eight shelves. Once the herd is bigger than what the oven can bake before the next customers arrive, the queue grows and the last orders wait for every duplicate ahead of them. Stampedes hurt most exactly when the database is already slow.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1What is a cache stampede, and why can it make the database slower than having no cache at all?
A good answer coversA hot entry expires and every request that arrives before it is rebuilt misses at the same moment and runs the same expensive query. The database sees a sudden burst of identical work it was never sized for (the cache was hiding that load), queues, slows down, and the slowdown keeps the entry empty longer, so even more requests miss.
Q2Why do deploys and cold starts cause synchronised expiry, and what does TTL jitter do about it?
A good answer coversA deploy or warm-up fills many keys within a few seconds, all with the same TTL, so they all expire together one TTL later and again after that. Multiplying each TTL by a small random factor (say 0.8–1.2) spreads those expiries over a window, so the refresh load arrives as a trickle the database can absorb.
Q3How does request coalescing (single-flight) work, and what does it not solve across many app servers?
A good answer coversEach process keeps a map of in-flight refreshes per key; a miss that finds one waits on it instead of starting its own, so one query serves everyone. It works per process: with 50 instances you still get up to 50 queries per expiry. For one query in total you need a shared lock or lease (with a timeout, in case its holder dies), or you accept N.
Q4What does stale-while-revalidate trade, and where would you not use it?
A good answer coversIt keeps serving the expired value while one background refresh runs, so nobody waits and the database sees one query. The trade is freshness: readers can see data slightly older than the TTL. Fine for catalogues, feeds and counts; not for balances, permissions or anything where an old value causes a wrong decision.
Q5What is probabilistic early expiration (XFetch), and why does it avoid a stampede without any coordination?
A good answer coversEach request that hits a value near the end of its TTL refreshes it early with a probability that rises as expiry approaches (and with how slow the recompute is). Some request almost always refreshes the key just before it expires, so it never actually goes missing, and no lock or shared state is needed.
Q6Every hour on the hour your database CPU spikes for 30 seconds and the slow-query log shows the same query hundreds of times. Diagnose it and list the fixes you would try, in order.
A good answer coversMany keys cached at the same time with a one-hour TTL, expiring together and stampeding. In order: add TTL jitter; coalesce refreshes per key (single-flight, or a lock with timeout across instances); serve stale while revalidating where freshness allows; refresh early (XFetch or a background job) for the hottest keys; and make the query itself cheaper or rate-limited so a herd can't take the database down.
