Systems lesson 17 · Race conditions

Race Condition Workbench

A race condition happens when two requests read the same thing, both decide what to write, and one quietly undoes the other. Nothing crashes, so it hides until there is real traffic. This lesson builds that idea three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, averaged over eight seeded runs of 100 deposits per clerk unless noted.

1. Two clerks, no protection

Experiment 1 of 5
2 clerks × 100 deposits each · read the card, work out the new balance at the desk (1 s), walk back and write it
How many of the 200 deposits never reach the card?

Each write puts down "what I read, plus 10". If the other clerk wrote in between, that write is replaced by a balance that never included it. Nothing crashes and every clerk thinks they succeeded; the money just isn't there. The longer the gap between reading and writing, the more often someone else writes inside it.

2. Take the key first

Experiment 2 of 5
4 clerks · a clerk takes the key from the hook before reading and hangs it back after writing
Nothing is lost now. What happens to deposits per minute compared with no protection?

The lock makes the whole read-think-write one at a time, including the walk and the thinking. Three clerks stand at the hook while one works. Correct, but the office now runs at the speed of one clerk. Keep what you do while holding a lock as short as possible.

3. Check the version

Experiment 3 of 5
Compare-and-swap: the card carries a version number; a write only lands if the version is still the one the clerk read, otherwise the clerk reads again and redoes the sum
Going from 2 clerks to 4, what happens?

Compare-and-swap is optimistic: it assumes nobody else wrote, and pays only when someone did. With more clerks, more writes land inside each clerk's window, so more work is thrown away and redone. Best of all is to not read at all: an atomic increment (UPDATE accounts SET balance = balance + 10) is one step, so there is no window to race in.

4. Check, then book

Experiment 4 of 5
3 clerks fill 24 seats · each checks the board for a free seat, fills in the form at the desk, then pins the seat
Every clerk checked the seat was free. How many seats end up booked twice?

"Check, then act" has the same gap as read-modify-write: the seat was free when the clerk looked, not when they pinned it. Customers like the same front-row seats, which makes clashes more likely. The fix is to make the act carry the check: pin only if still free (a conditional update), or let the database refuse a second booking (a unique constraint on the seat).

5. It passed locally

Experiment 5 of 5
The same unprotected code · 1 clerk (a unit test), 2 clerks at a quiet moment (a manual test), 4 clerks when the office is busy (production)
What do the tests show?

A race needs two clerks inside the same window. One clerk can never race with itself, and two clerks at a quiet moment rarely overlap. Production has many requests at once, so the bug shows up only there, and it isn't reproducible on demand. Find races by reading the code for read-then-write and check-then-act, and test them with many concurrent requests on purpose.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1Two requests run `balance = get(); set(balance + 10)` at the same time. Explain how money disappears.
A good answer coversBoth read the same balance, say 100. Each adds 10 and writes 110. Two deposits happened, but the balance only went up once. Neither request failed, so nothing is logged; the second write simply replaced the first.
Q2Name three ways to fix a lost update on a database row, and when you'd pick each.
A good answer coversAn atomic update in one statement (UPDATE … SET balance = balance + 10): the best when the change can be expressed that way. Optimistic locking (a version column, UPDATE … WHERE version = 7, retry on 0 rows): good when conflicts are rare. A lock (SELECT … FOR UPDATE, or a mutex): when the change needs a long read-modify-write and conflicts are common, keeping the locked section short.
Q3Why can a lock make a fast system slow, and how do you avoid that?
A good answer coversEverything inside the lock runs one at a time. If the locked section includes slow work (a network call, a heavy computation, waiting for a user), every other request queues behind it. Do the slow work before taking the lock, keep only the read and write inside it, or avoid the lock with an atomic operation.
Q4What is check-then-act, and what is a real example in a web app?
A good answer coversChecking a condition and then acting on it as two separate steps: "is this username free? then create the user", "is the seat free? then book it", "is stock above 0? then sell". Between the check and the act, another request can make the check false. Fix it by making the database enforce it: a unique constraint, a conditional update, or an insert that fails on conflict.
Q5Your tests pass but production has a lost-update bug. Why didn't the tests catch it, and how would you write a test that does?
A good answer coversTests usually send one request at a time, so two requests never overlap inside the read-write window. Write a test that fires many concurrent requests at the same record (and add a small delay between read and write to widen the window), then check the final value equals the number of successful requests.
Q6Compare-and-swap never loses an update. Why might it still be the wrong choice?
A good answer coversUnder heavy contention most attempts fail and get retried, so the same work is done many times, latency grows and some requests can starve. If the update can be one atomic operation, use that; if contention is high and the work is long, a short lock or a queue that serialises updates per record may be better.
