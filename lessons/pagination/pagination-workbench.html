Systems lesson 12 · Pagination

Pagination Workbench

Every list API has to hand data out a page at a time, and the way it remembers where the last page ended decides how fast deep pages are and whether rows get shown twice or never. This lesson builds offset and cursor pagination three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, on a 2,000-row table (20,000 for the deep page), averaged over eight seeded readers where timing is random.

1. A deep page

Experiment 1 of 5
20,000 rows, 20 per page · page 1 vs page 500
How much more work is page 500 than page 1?

OFFSET 9980 doesn't jump anywhere: the database finds the first 9,980 rows in order and throws them away before returning 20. The work grows with the page number. A cursor (WHERE (created_at, id) < (last values) ORDER BY … LIMIT 20) seeks straight into the index at the last row and reads 20, so page 500 costs what page 2 costs.

2. New rows while you page

Experiment 2 of 5
Offset paging, 10 pages of 20, newest first · about one new row per second while the reader pauses 2 s between pages
What does the reader see?

Every new row lands at the front and pushes everything one place back. The next OFFSET then starts that many places too early, so the last rows of the previous page show up again. A cursor asks for rows older than the last one it saw, so new rows at the front don't move its starting point.

3. Rows deleted while you page

Experiment 3 of 5
Offset paging, 10 pages of 20 · about one row deleted per second from the rows being paged
Now rows disappear from pages already read. What does the reader miss?

A delete in a page you've already read pulls every later row one place forward, so the next OFFSET starts one row too late and silently skips a row that still exists. Nobody gets an error; the row just never appears. A cursor continues after the last row it saw, wherever that row now sits.

4. A cursor on created_at alone

Experiment 4 of 5
Cursor paging, 10 pages of 20 · rows are imported three per second, so created_at has ties · cursor key created_at vs (created_at, id)
With WHERE created_at < :last, what happens at page boundaries?

When a page ends in the middle of a second, the other rows from that same second are not older than the last one shown, so WHERE created_at < :last skips them. Changing < to <= repeats them instead. The fix is a unique cursor: order by (created_at, id) and compare the pair, with an index on both columns.

5. Jump to page 37

Experiment 5 of 5
20 per page · a user clicks page 37 directly
How does each kind of pagination get there?

A cursor only knows where the last page ended, so there is no cursor for page 37 until you've fetched pages 1 to 36. Offset can compute it: OFFSET 720. That's the trade: offset gives page numbers but gets slower and drifts as data changes; cursors are fast and stable but only go next and previous. Infinite scroll and APIs suit cursors; numbered pages over small or stable data suit offset.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1What does OFFSET 10000 LIMIT 20 make the database do?
A good answer coversRead the first 10,020 rows in sort order (through the index or a sort) and throw away 10,000 of them. The cost grows with the offset, so deep pages get slow and use more I/O even though the result is the same 20 rows.
Q2Write the WHERE clause for the next page of a feed ordered by created_at DESC, id DESC, and the index it needs.
A good answer coversWHERE (created_at, id) < (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20, with an index on (created_at, id). Where row-value comparison isn't supported: created_at < :t OR (created_at = :t AND id < :id).
Q3A user reports seeing the same item twice while scrolling a busy feed, and support can't reproduce it. What's your first guess?
A good answer coversOffset pagination over data that changes: new items arrived between page requests and pushed earlier items onto the next page. Deletes cause the opposite, silently skipped items. Moving to a cursor fixes both.
Q4Why is a cursor on created_at alone a bug, and when does it show up?
A good answer coverscreated_at isn't unique. When a page ends partway through rows with the same timestamp (bulk imports, coarse clocks, high write rates), the rest of them are skipped (with <) or repeated (with <=). Add a unique tiebreaker such as id to the order and the cursor.
Q5Product wants numbered pages with a page picker. When is offset pagination fine?
A good answer coversWhen the data is small or changes rarely (an admin table, search results capped at a few hundred), and users rarely go deep. Otherwise cap the page depth, or show next/previous with a cursor and offer search or filters instead of page 400.
Q6What should a cursor in an API response look like?
A good answer coversOpaque to the client: an encoded token (for example base64 of the last created_at and id), returned as next_cursor and passed back as a parameter. Clients shouldn't build or parse it, so you can change the sort or the key later without breaking them.
