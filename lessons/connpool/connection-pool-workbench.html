Systems lesson 29 · Connection pooling

Connection Pool Workbench

Opening a database connection is slow, and a database can only hold so many. A pool keeps a few open and lends them out; most connection trouble comes from sizing it, holding a connection too long or never giving it back. This lesson builds a pool as a taxi rank: watch it work, predict what breaks it, then explain it back.

01

The machine

Each hotel is an app instance with its own rank of cabs, its connection pool. A passenger takes a cab to the terminal (the database) and back; a cab at the kerb is a query running. Every cab that exists holds one of the terminal's 60 permits. Try no pool, a bigger pool, an API call inside the transaction, a leak, and scaling out to four hotels.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, run at full speed and averaged over six seeded runs.

1. A new connection for every request

Experiment 1 of 5
No pool · each request opens its own connection, uses it once and closes it · 2 instances, 60 requests/s each
The queries take about 10 ms. How long does a typical request take now?

Before a new connection can run anything it needs a TCP handshake, TLS and authentication, and the database starts a fresh backend for it: about 30 ms here. The query still takes 10 ms, so setup costs three times the useful work on every single request. A pool pays that once and then reuses the connection thousands of times.

2. A bigger pool

Experiment 2 of 5
2 instances at 500 requests/s each, more than the database can serve · pool per instance 5 → 10 → 20 (up to 10, 20 or 40 queries at once)
Which pool size gets the most requests served per second?

The database does its best work with only a few queries at once, about twice its cores. Past that, extra queries add no capacity; they fight over CPU, locks and cache and slow every query down. With 40 connections each query takes 8 times longer and fewer finish per second. When demand exceeds capacity, a small pool keeps the excess waiting in the app, where waiting is cheap, instead of inside the database.

3. One code path forgets to give it back

Experiment 3 of 5
1 request in 500 returns early without releasing its connection · 2 instances, pool 10, 60 requests/s each, for 5 minutes (Watch uses 1 in 50 at ×8, so the lots fill while you look)
What do you see over those 5 minutes?

A leaked connection is still checked out, so the pool can neither use it nor replace it. At 60 requests a second the tenth leak comes after about 5,000 requests, and from then on every request waits its full second and times out, while the database sits idle holding 20 connections that do nothing. It passes every short test. Release connections in a finally block (or with try-with-resources / using), and turn on the pool's leak detection.

4. An API call inside the transaction

Experiment 4 of 5
Each request calls an external API (200 ms) while holding its connection, instead of before taking one · 2 instances, pool 10, 60 requests/s each
The database runs exactly the same queries. What happens?

A connection is busy for as long as someone holds it, not only while a query runs. 60 requests a second, each holding one for 210 ms, need about 12.6 connections at once; the pool has 10. The wait queue grows until requests time out, yet the database runs about one query at a time. Do slow outside work before or after the transaction, never inside it.

5. Scale out for a busy day

Experiment 5 of 5
Pool 20 per instance, the database allows 60 connections · scale from 2 to 4 instances · then the same through a pooler that keeps 20 server connections
Connecting directly, what happens when the extra instances start?

Each instance opens its full pool of 20 at start-up. Three instances already hold all 60 connections the database allows, so the fourth is refused every time it tries: its rank stays empty and all its requests fail, a quarter of all traffic. Autoscaling multiplies pools. A pooler such as PgBouncer lets many cheap client connections share a few server connections, so the database only ever sees 20.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1Why is opening a database connection per request slow, and what exactly does a pool save?
A good answer coversA new connection needs a TCP handshake, a TLS handshake and authentication (several network round trips), and the database starts a backend process or thread and allocates memory for it. That often costs more than the query. A pool opens connections once and lends them out, so each request only pays for its queries.
Q2Your service handles 300 requests a second and each holds a connection for 20 ms. How many connections does it need, and why not just configure 200?
A good answer coversLittle's law: 300 × 0.020 = 6 connections busy on average; add headroom for bursts, so perhaps 10–15. Not 200: under load, more connections means more concurrent queries in the database, which past roughly twice its cores slows every query down, and every connection costs database memory even when idle.
Q3Why can a bigger pool make a busy system slower?
A good answer coversThe database has a fixed amount of CPU, disk and lock capacity. Beyond a few active queries per core, extra queries don't add throughput; they add context switching, lock and cache contention. A smaller pool keeps the excess queued in the application, where waiting costs almost nothing, and the database stays at its most efficient level.
Q4A service runs fine for an hour after each deploy, then every request fails with 'timed out waiting for a connection'. The database looks idle. What do you suspect, and how do you confirm it?
A good answer coversA connection leak: some code path never returns its connection. Confirm with pool metrics (active = maximum while throughput is near zero), pg_stat_activity showing sessions idle or 'idle in transaction' for a long time, and the pool's leak-detection log, which prints the stack trace of who borrowed it. Fix with finally / try-with-resources / using.
Q5Why shouldn't you call an external API inside a database transaction?
A good answer coversThe connection, and any locks the transaction holds, stay taken for the whole call. The pool runs out long before the database is busy, other requests time out, and a slow or hanging API now blocks your database work too. Fetch what you need before the transaction, or record the intent and call the API after commit (for example with an outbox).
Q6You run 30 pods with a pool of 10 each against a database with max_connections = 200. What happens, and what are your options?
A good answer covers30 × 10 = 300 connections wanted, 200 allowed: the last pods to start can't get connections and fail. Options: smaller pools per pod; a pooler such as PgBouncer in transaction mode so pods share a small set of server connections; or raising max_connections carefully, since each connection costs database memory. Count pods × pool size against the limit whenever you autoscale.
