Systems lesson 05 · Rate limiting

Rate Limiter Workbench

A rate limiter hands out permission at a fixed pace and says "not now" (HTTP 429) when it runs out. This lesson builds the token bucket three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, averaged over six seeded runs (60 s each unless noted).

1. A bigger bucket

Experiment 1 of 5
Bucket 8 tokens → 16 tokens · refill stays at 4 per second
Clients want more than the limit all the time. How many requests get through per minute now?

Over a long stretch, nothing can get through faster than tokens arrive: 4 per second is 240 per minute, plus one bucketful. The size only decides how big a burst can pass at once after a quiet spell. Size is the burst allowance; the refill rate is the limit.

2. The window boundary

Experiment 2 of 5
Fixed window (8 per 2 s) vs token bucket (4/s, holds 8) · a client sends 16 just before a window ends and 16 just after
With the fixed window, how many get through in that 0.4 s?

A fixed window only counts within its own window. 8 fit at the end of one window and 8 more at the start of the next, so twice the limit passes in less than half a second. A token bucket (or a sliding window) has no boundary to exploit: after the first 8 it only lets through what drips in.

3. One noisy client

Experiment 3 of 5
Client C sends 8 requests/s, A and B send 1/s · one shared limit of 6/s vs a third of it per client
With one shared limit, what happens to A and B?

A shared bucket doesn't know who is asking. C takes most of the tokens, so A and B find the tube empty as often as C does. A limit per client (per API key, per user, per IP) gives each its own tube, so C only drains its own.

4. Retrying on 429

Experiment 4 of 5
Client A bursts 30 requests at once · impatient clients retry every 0.25 s vs clients that wait the Retry-After time (plus jitter)
How many rejected attempts does the limiter see?

A rejected request costs the server something even if it does no work: a connection, parsing, a lookup. Clients that hammer every 0.25 s turn one burst into a stream of rejections. Waiting the Retry-After time, with jitter so they don't all return at once, sends far fewer. Impatient clients also grab tokens first, which is why well-behaved clients need the server to enforce fairness.

5. Two app instances

Experiment 5 of 5
1 → 2 app instances behind a load balancer · each keeps its own bucket in memory (4/s, holds 8)
Clients ask for 7.5 requests/s. How many get through per minute now?

Each instance enforces 4/s on the half of the traffic it sees, so together they allow 8/s. Every instance you add raises the real limit. A limit meant for the whole service needs one shared counter, usually in Redis, that every instance checks.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1A limit is set as "bucket 20, refill 5 per second". What does each number control?
A good answer coversThe refill rate is the long-run limit: never more than 5/s over time, 300 a minute. The bucket size is the burst allowance: after a quiet period, up to 20 can go through at once. Doubling the bucket doesn't raise throughput; doubling the refill does.
Q2Why is a fixed window easy to exploit, and what fixes it?
A good answer coversIt resets at fixed times, so a client can spend the whole limit just before the boundary and again just after, getting twice the limit in a moment. A token bucket or a sliding window (counting the last N seconds at any moment) doesn't have a boundary to exploit.
Q3Your API has one global limit and one customer starts a batch job. What do other customers see, and how would you design the limit instead?
A good answer coversThey get 429s too, because they share the same tokens. Limit per API key or per user (often with a global limit behind it to protect the service), so a noisy customer only exhausts their own allowance.
Q4What should a well-behaved client do when it gets a 429?
A good answer coversStop, wait at least the Retry-After time, add random jitter so many clients don't come back at the same instant, and back off further if it keeps getting 429s. Retrying immediately multiplies the load on a server that is already saying it's busy.
Q5You run 4 replicas, each with an in-memory limiter of 100 requests/s. What is the real limit, and how do you get a true 100/s?
A good answer coversAbout 400/s, and it changes whenever you scale. Keep the counter in a shared store such as Redis (an atomic increment or a small Lua script per request), or rate limit at the gateway in front of the replicas.
Q6Where does rate limiting belong: the API gateway, each service, or the client?
A good answer coversUsually more than one: the gateway or edge for coarse per-client limits that stop abuse early, services for limits that protect a specific expensive resource, and clients for politeness (honouring Retry-After, backing off). Each layer protects something different.
