Systems lesson 24 · Outbox pattern

Outbox Workbench

Most requests have to do two things: save something in the database and tell other services about it. Done as two separate writes, a failure in between leaves them disagreeing, and nothing reports it. This lesson builds the outbox pattern: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine: 10 minutes of orders, averaged over eight seeded runs.

1. Fail between the two writes

Experiment 1 of 5
Write the ledger, then post the letter · the clerk fails on the way to the postbox for 1 order in 20 · 10 minutes of orders
Every ledger write succeeds before the clerk sets off. What does the warehouse end up with?

The ledger commit and the letter are two separate writes to two separate systems. When the process dies between them, the first is permanent and the second never happens. The customer was told yes, the database has the order, and the warehouse will never ship it. No error is raised anywhere, because each write that ran, worked.

2. Send first, then write

Experiment 2 of 5
Swap the order: post the letter, then write the ledger · the ledger write fails for 1 order in 20
Does sending first fix it?

Swapping the writes swaps the failure. The letter is already on its way when the ledger write fails, so the warehouse ships an order that, as far as your database is concerned, never happened: the customer got an error and may order again. Watch the bin fill with failed cards while SHIPPED runs ahead of ORDERS.

3. Put the letter in the outbox

Experiment 3 of 5
The ledger card and the letter go into the cabinet in one transaction · a relay posts pending letters and then marks them sent · clerk fails 5%, relay fails 10% after posting, before marking
What happens to lost and phantom orders now, and what new thing appears?

One transaction writes both rows or neither, so a failed clerk leaves no order and no letter: the customer gets an error and can retry. The relay only marks a letter sent after posting it; if it fails in between, the letter is still pending and gets posted again. That is at-least-once delivery: nothing is lost, and some letters arrive twice.

4. The warehouse ships every letter

Experiment 4 of 5
Outbox, relay fails 10% after posting · warehouse dedupe off vs on (it keeps the order numbers it has seen and drops repeats)
With dedupe off, what does the warehouse do with the repeated letters?

At-least-once delivery moves the problem to the consumer: it must be idempotent. Keep the IDs of events you have handled (or make the handler an upsert keyed by the order), and a second copy changes nothing. The outbox and an idempotent consumer together give the effect of exactly-once.

5. A slower relay

Experiment 5 of 5
Outbox, nothing fails · the relay checks the outbox every 0.5 s, 2 s or 5 s · compared with walking the letter straight over
What does a longer poll interval cost?

Each letter waits in the outbox until the next check, on average about half the interval, plus the trip. The guarantee is the same at any interval; only latency (and how often you query the database) changes. Change data capture, which tails the database's log instead of polling the table, gets the wait close to zero.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1A handler saves an order and then publishes an "order placed" event. Both calls succeed in all your tests. What can still go wrong in production?
A good answer coversThe process can die, be redeployed or time out between the two calls. The order is committed, the event is never published, and downstream services never hear of it. Nothing errors, so it shows up later as an order that never shipped.
Q2Why doesn't publishing first, then saving, fix it?
A good answer coversIt flips the failure: if the save fails after the publish, consumers act on an order your database doesn't have. A phantom is often worse than a loss, because other systems have already shipped, charged or emailed.
Q3How does the outbox make the two writes atomic, and what does it rely on?
A good answer coversThe event is written as a row in an outbox table in the same database transaction as the business change, so both commit or neither does. It relies on that single local transaction; a separate process then reads the outbox and publishes.
Q4Why does the relay deliver at least once instead of exactly once, and what does that ask of consumers?
A good answer coversIt can only mark a row sent after the broker accepts it; if it crashes in between, it publishes the row again on restart. Consumers must be idempotent: dedupe by event ID, or make the effect an upsert keyed by the business ID.
Q5Polling the outbox table or change data capture (reading the database log, for example with Debezium): what is the trade-off?
A good answer coversPolling is simple and works anywhere, but adds latency (about half the interval) and query load. CDC publishes within milliseconds and doesn't query the table, but needs log access, a connector to run and operate, and care with schema changes.
Q6How do you keep events for one order in order, and what happens to the outbox table over time?
A good answer coversPublish rows in commit order per aggregate and use the order ID as the partition key, so one partition (and one consumer) sees them in sequence; don't publish one aggregate's rows in parallel. Sent rows are deleted or archived on a schedule, or the table grows forever.
