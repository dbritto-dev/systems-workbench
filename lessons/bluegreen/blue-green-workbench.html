Systems lesson 09 · Blue-green deploys

Blue-Green Workbench

Run two complete copies of production. Deploy the new version to the idle one, then move all traffic over with one switch, and keep the old one ready to switch back. This lesson builds that idea three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the figure, averaged over six runs: requests arrive at 5 per second, and each line has three presses.

1. Roll back a bad release

Experiment 1 of 5
Green ships with a bug that fails 40% of requests · the alarm fires 15 s after the flip
You roll back by flipping the gate back to blue. How long until errors stop, compared with redeploying the old version server by server (one minute each)?

Blue never went away. It is still running the old version, with a warm cache, so flipping back is just a change of route. A rolling redeploy has to rebuild each server, and every minute it takes, the servers still on the bad version keep failing requests.

2. What it costs

Experiment 2 of 5
A normal deploy · blue is kept running after the flip so you can roll back
What do you pay for that instant rollback while the deploy is in progress?

Both sides are full production: same number of servers, same connections to the database. While one is live the other does nothing but wait. That is the price of being able to flip back instantly. Rolling deploys only add one spare server at a time, and pay for it with slow rollbacks.

3. A cold green

Experiment 3 of 5
Green starts with an empty cache · you flip as soon as it is up
Right after the flip, what happens to latency?

Every request misses on a cold cache, misses take four times longer, and three workers can't keep up with the traffic until the cache fills. The queue fills, and once it is full new requests are turned away. Warming green first (replaying traffic, or preloading the hot keys) makes the flip a non-event.

4. Flip without draining

Experiment 4 of 5
Draining off · blue stops the moment the gate flips
What happens to the requests already on blue's lane, in its queue or under its presses?

Those requests were already routed. If blue stops at the flip, they are cut off and their clients get errors. With connection draining, blue takes no new requests but finishes the ones it has, so the switch drops nothing.

5. A migration blue can't read

Experiment 5 of 5
Green's migration drops a column blue still reads · then green turns out to be bad
You flip back to blue. What happens?

The database is shared. Green's migration changed it for both sides, so the rollback brings back code that no longer matches the schema. Blue-green only rolls back code. Migrations have to work for both versions: add the new column first (expand), switch the code, and drop the old one only after blue is gone for good (contract).

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1Why is rolling back a blue-green deploy so much faster than rolling back a rolling deploy?
A good answer coversBlue is still running the old version, warm, so rollback is only a change of route at the gate. A rolling rollback has to rebuild servers one by one, and the bad version keeps serving traffic until the last one is replaced.
Q2Your manager asks why the deploy doubles the cloud bill for an hour. How do you explain it, and when is it worth it?
A good answer coversBoth sides are full production while the old one is kept for rollback, and the idle one does no work. It is worth it when a bad release is expensive and you need to undo it in seconds; for small, low-risk services, a rolling or canary deploy may be the better trade.
Q3What would you do before flipping to a freshly deployed green, and why?
A good answer coversWarm it: let its caches fill, open its connection pools, run smoke tests against it. Otherwise the first minute after the flip runs on cold caches with slow misses, latency spikes and requests may be turned away.
Q4What is connection draining, and what goes wrong without it?
A good answer coversThe old side stops taking new requests but finishes the ones it already has before shutting down. Without it, requests that were routed just before the flip are cut off and fail.
Q5Green needs to rename a column. How do you ship that with blue-green and still be able to roll back?
A good answer coversExpand and contract: add the new column and write both, deploy green reading the new one, keep the old column until blue is gone and rollback is no longer needed, then drop it in a later deploy.
Q6Blue-green flips all traffic at once. What risk does that leave that a canary deploy reduces?
A good answer coversEvery user hits the new version at the same moment, so a bug that only shows under real traffic affects everyone until the rollback. A canary sends a small share first, so only a few users see the bug.
