Systems lesson 06 · Retry storms

Retry Storm Workbench

A retry feels like the safe thing to do: if a call fails, try again. When many clients do it at once, retries can keep a system overloaded long after the original problem is gone. This lesson shows how that happens, and what actually stops it.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same office, averaged over 16 two-minute runs after a rush of 16 visitors.

1. Three quick retries

Experiment 1 of 5
No retries → 3 retries, sent at once · then a rush of 16 visitors
Without retries, the trouble from a rush is over in about ten seconds. With three immediate retries, how long does it last?

Every client that times out leaves its ticket in the line, and the window still serves it for nobody. Then the client queues again, and again. The line gets longer, so more clients time out, so more tickets are added: up to four per request. The window spends its time on abandoned tickets, and the rush is self-sustaining even after every visitor has left.

2. Wait before retrying

Experiment 2 of 5
Immediate retries → exponential backoff · wait 2, then 4, then 8 s
Clients now wait on the benches before trying again. What happens after the rush?

While clients sit on the benches they are not adding tickets, so the window catches up and the storm ends. But the rush's visitors all timed out at the same moment, so they all wait exactly 2 s, come back together, time out together, and wait exactly 4 s. You can see them clumped on the same bench.

3. Add jitter

Experiment 3 of 5
Exponential backoff → backoff with jitter · each wait spread between ½ and 1½ times its delay
The average wait is exactly the same as before. What does jitter change?

Jitter breaks up the clump: clients that failed together now return at different moments, so the window sees a trickle instead of a wave, and the tallest spike is far lower. It does not reduce how many retries there are, so the total work, and the time to recover, stay about the same. Jitter protects against spikes; budgets and backoff reduce work.

4. A timeout that's too short

Experiment 4 of 5
Timeout 3 s → 0.8 s · the window normally takes 0.7 to 1.3 s · no rush
Nothing else is wrong. With three retries, what share of the window's work reaches a client who is still waiting?

Most requests take longer than 0.8 s even with an empty line, so the client gives up while the window is still working on it, then sends another. The window finishes every ticket anyway. Load more than triples and almost nothing useful comes out. A timeout must sit above the normal, slow-end latency of what you call, not at its average.

5. Retries at every layer

Experiment 5 of 5
1 layer retries → 3 layers retry (app, client library, proxy) · 3 retries each
In the worst case, how many attempts reach the window for one request?

Retries multiply, they don't add: 4 × 4 × 4 = 64 attempts for one request. During the storm the office measured above 30 attempts per request. Retry at one layer only, usually the one nearest the user, and give it a budget: here retries may be at most about 10% of new requests, so once the window struggles, clients fail fast instead of piling on.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1Why can a ten-second rush turn into an outage that lasts after the rush is gone?
A good answer coversClients time out and retry, but the server still does the work for the abandoned attempts. More attempts make the line longer, which makes more clients time out, which adds more attempts. The system settles in a state where it is fully busy with work nobody is waiting for. Removing the original cause doesn't fix it; reducing load does.
Q2Backoff ended the storm in the office. Why might it not in a system where new users keep arriving at a fixed rate?
A good answer coversIn the office, clients on a bench are not sending anything, so backoff lowers the load. When new requests keep arriving regardless, backoff only delays retries: every failed request still sends all its attempts eventually, so the total load can stay above capacity. That's why retry budgets and circuit breakers, which cap the number of retries, are needed on top.
Q3If jitter doesn't change the average wait, why does it matter?
A good answer coversClients that failed at the same moment retry at the same moment. Those waves hit the server as spikes, which make queues long right then and cause more timeouts. Jitter spreads them out so the server sees a steady trickle. It reduces peaks, not the total number of retries.
Q4How would you choose a client timeout for a call that normally takes 50–200 ms?
A good answer coversAbove the slow end of normal latency (the p99 or so), not the average, with some room: maybe 500 ms to 1 s. Pair it with a deadline the server can see, so it can drop work for clients that have already given up instead of finishing it.
Q5A request goes app → client library → proxy → service, and each retries 3 times. What would you change?
A good answer coversRetry in one place only, usually the outermost layer that knows whether retrying is safe and useful, and make the others fail fast. Worst case is 4 × 4 × 4 = 64 attempts otherwise. Add a retry budget so retries stop when the error rate is high.
Q6What does a retry budget do, and what should the client do when it's empty?
A good answer coversIt caps retries at a share of normal traffic, e.g. 10%. When most calls fail, the budget runs out quickly and the client fails fast instead of multiplying load. The client returns an error or a fallback right away, and a circuit breaker can stop calls entirely until the service recovers.
