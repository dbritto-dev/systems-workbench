Systems lesson 15 · Async I/O

Async Workbench

Async I/O lets one worker start many slow operations and handle each result when it is ready, instead of standing still while it waits. This lesson builds that idea three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results are averaged over six seeded runs of the same model the figure runs.

1. Four waiters or one

Experiment 1 of 5
100 orders · each waits 200 ms in the kitchen · 4 blocking threads vs 1 async waiter
Which finishes the 100 orders faster?

A blocking thread spends almost all of its time standing at the window. Four threads can only have four orders in the kitchen at once, so 100 orders take 25 rounds of 200 ms. The async waiter clips a ticket on the rail and goes straight back for the next order, so the kitchen gets all 32 burners busy. Waiting doesn't need a pair of hands, only a ticket.

2. Orders that need real work

Experiment 2 of 5
100 orders · 40 ms of CPU each, 10 ms in the kitchen · 4 blocking threads vs 1 async waiter
Now most of the time is spent working, not waiting. Which is faster?

Async only removes waiting. Here every order needs 40 ms of hands-on work, and there is one pair of hands (one CPU core), so 100 orders take about 4 seconds however you schedule them. To go faster you need more cores working at the same time: parallelism, which is a different tool (lesson 14).

3. Await in a loop

Experiment 3 of 5
20 orders · async · `for … await` one by one vs `Promise.all` / `asyncio.gather`
How much faster is gathering them?

Awaiting inside a loop sends one order, waits for it to come back, then sends the next: async syntax, sequential behaviour. Gathering puts all 20 tickets on the rail at once, so they cook side by side and the batch takes about one kitchen trip. Await in a loop is right only when each call needs the previous result.

4. Gather a thousand

Experiment 4 of 5
1,000 orders · gather all at once vs at most 20 in flight · the kitchen has 32 burners, calls time out after 2 s
Which way gets more orders delivered?

Gathering everything floods the kitchen: 32 burners serve about 160 orders a second, so the queue grows by hundreds and most orders wait past the 2 s timeout and fail, after the kitchen did part of the work. A semaphore keeps no more in flight than the kitchen can cook, so nothing times out. The right limit is about the dependency's capacity, not your own.

5. One blocking call

Experiment 5 of 5
100 orders · async · each handler also reads a file synchronously for 15 ms
What happens to the batch?

A synchronous call inside async code blocks the only pair of hands. While the waiter reads, nobody takes orders and nobody answers the bell, so 100 reads add 1.5 seconds of frozen time for everyone and finished dishes wait over a second to be picked up. Use the async version of the call, or hand it to a worker thread.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1Why does one async waiter deliver more than four blocking threads when the work is mostly waiting?
A good answer coversA blocking thread is occupied for the whole wait, so throughput is threads ÷ time per order. Async keeps many orders in flight with one thread: it only needs a ticket per wait, not a thread, so throughput is limited by how many calls the dependency can handle at once.
Q2When does async not help, and what do you use instead?
A good answer coversWhen the work is CPU-bound: there is nothing to overlap, the core is busy the whole time. You need parallelism (more cores: processes, worker threads) or less work per request (caching, better algorithms).
Q3`for (const id of ids) await fetchUser(id)` is slow. When is that loop still the right choice?
A good answer coversWhen each call depends on the previous result, when order matters, or when the other side can only take one at a time. Otherwise gather them, with a limit.
Q4What can go wrong with `Promise.all` over 10,000 items, and how do you fix it?
A good answer coversEvery call starts at once: the dependency gets flooded, calls time out, retries add more load, and memory grows with every pending call. Bound it with a semaphore or a pool (p-limit, asyncio.Semaphore, a worker pool) sized to what the dependency can serve.
Q5Someone adds `fs.readFileSync`, `time.sleep` or a synchronous HTTP client inside an async handler. What happens in production?
A good answer coversIt blocks the event loop for every request, not just this one: no new requests are picked up and finished ones aren't handled until it returns. Latency rises for everyone. Use the async version or move the call to a thread pool (`asyncio.to_thread`, a worker thread).
Q6How would you pick the concurrency limit for calls to a database that holds 32 connections?
A good answer coversStart from the dependency's capacity: about 32 in flight keeps it busy without queueing. Little's law gives the throughput: in-flight ÷ time per call, so 32 ÷ 0.2 s ≈ 160 calls a second. Then measure, and leave room for other clients sharing it.
