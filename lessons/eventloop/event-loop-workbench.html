Systems lesson 16 · The event loop

Event Loop Workbench

JavaScript runs your code on one thread, one task at a time. Everything else, from timers to network replies to drawing the screen, waits for that one thread to be free. This lesson builds that idea three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the figure, averaged over four 3-second runs of loop time.

1. One long job

Experiment 1 of 5
CPU job none → 200 ms of synchronous work every half second · setTimeout(…, 10) still armed every 100 ms
What happens to a timer that is due 10 ms from now while the job runs?

The timer is kept outside the loop, and it does become due on time: it drops onto the conveyor after 10 ms. But only the operator runs callbacks, and the operator is busy with the job. Nothing interrupts running JavaScript, so the callback, every I/O callback and every frame wait their turn behind it. A delay is a minimum, never a promise.

2. Who goes first

Experiment 2 of 5
One script: setTimeout(cb, 0), then Promise.resolve().then(cb), then console.log(…)
In what order do the three run?

The script itself is on the stack, so its console.log runs first. When it ends, the operator empties the microtask tray before touching the conveyor, so the promise callback runs next. The timer callback, even with a delay of 0, is a macrotask: it waits on the conveyor until the stack and the tray are both empty.

3. A promise chain that never yields

Experiment 3 of 5
Promise chain on · 400 callbacks of 0.5 ms, each queuing the next
Each callback is tiny. What happens to I/O callbacks and frames while the chain runs?

The rule is to empty the microtask tray completely before anything else. A callback that queues another callback keeps the tray from ever being empty, so 400 small steps behave like one 200 ms block. This is how code full of await, with no long function anywhere, can still freeze a page or stall a server.

4. Split the job

Experiment 4 of 5
200 ms job → 40 chunks of 5 ms, each queued at the back of the conveyor
What happens to the longest gap between frames, and to how long the job takes?

Each chunk goes to the back of the line, so timers, I/O callbacks and frames slip in between. Nobody waits more than one chunk. The total work is the same, plus everyone else's turns in between, so the job itself finishes a little later. You trade a little throughput for a lot of responsiveness.

5. Hand it to a worker

Experiment 5 of 5
200 ms job → posted to a worker thread; the result comes back as a message
What happens to the loop, and to how long the job takes?

A worker is a second thread with its own loop. The main loop only spends half a millisecond posting the job and one millisecond handling the result, so timers and frames stay on time. The job is not faster: the same 200 ms of work happens on another core. Workers cost memory and a copy of the data, so they suit heavy, self-contained work.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1setTimeout(fn, 10) ran 180 ms late. Nothing was wrong with the timer. What was?
A good answer coversSomething else held the call stack: a long synchronous function, a big JSON.parse, a loop over a large array, or a chain of microtasks. The delay only says when the callback may run at the earliest. It runs when the stack is empty and the microtasks are drained.
Q2Why do promise callbacks run before a setTimeout(0) callback queued earlier?
A good answer coversPromise callbacks are microtasks, timer callbacks are macrotasks. After each macrotask the loop empties the whole microtask queue before it takes the next macrotask or draws a frame. Queue order only matters within the same queue.
Q3A page freezes but the profiler shows no single long function, only thousands of tiny async callbacks. How is that possible?
A good answer coversA chain of microtasks (a recursive .then, an await inside a tight loop that never really waits) keeps the microtask queue from emptying, so frames, timers and I/O never get a turn. The fix is to yield to the macrotask queue (setTimeout, setImmediate, scheduler.yield) every so often, or to batch the work.
Q4Your Node API has to parse a 50 MB JSON upload. What are the options, and what does each cost?
A good answer coversParsing it on the main thread blocks every other request for the whole parse. Splitting the work keeps the loop responsive but makes this request slower. A worker thread keeps the loop free but costs memory and a copy of the data. A streaming parser avoids holding it all at once. Moving the work to a queue and a separate service removes it from the API entirely.
Q5Node reads files on a pool of four helper threads. What happens if 20 slow file reads arrive at once?
A good answer coversFour run, sixteen wait for a free helper, and their callbacks arrive later. DNS lookups and some crypto use the same pool, so they wait too. The pool size can be raised (UV_THREADPOOL_SIZE). Network sockets don't use the pool, because the operating system already does them asynchronously.
Q6What would you measure in production to catch these problems early?
A good answer coversEvent-loop delay (for example perf_hooks.monitorEventLoopDelay in Node or the long-task API in browsers): how late a timer that should fire every few milliseconds actually fires. A rising p99 delay means something is holding the stack, long before users complain about timeouts.
