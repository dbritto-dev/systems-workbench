Systems lesson 27 · N+1 queries

N+1 Query Workbench

A list page runs one query for the list, then one more for each row's related data: N + 1 queries where 2 would do. Each is a round trip, so the page costs the number of rows times the distance to the database. This lesson shows it as a warehouse picker: watch the trips, predict what makes them worse, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, averaged over eight seeded pages.

1. The database moves away

Experiment 1 of 5
N+1 · 20 orders, 5 items each · database on the same host (0.2 ms round trip) → in another zone (10 ms)
The page runs the same 21 queries and fetches the same 28 KB. How long does it take now?

Each query waits for a full round trip before the next one starts, so the page costs about 21 × the round trip. On your laptop the trip is a fraction of a millisecond and the N+1 hides; in production, with the database a zone away, the same code is twenty times slower. The bytes barely matter: the trips do.

2. A bigger page

Experiment 2 of 5
Database in another zone · orders per page 20 → 50 · N+1 vs batched (one IN query for all the items)
How does the page time change for each?

N+1 runs one query per order, so its trips, and its time, grow with the page: 21 trips become 51. The batched page always runs two queries (the orders, then every item WHERE order_id IN (...)), whatever the page size. Its second query returns more rows, but shipping a few more kilobytes costs far less than thirty more round trips.

3. One more level

Experiment 3 of 5
N+1 · 20 orders, 5 items each · the page now also shows each item's product, loaded the same lazy way
How many queries does one page run now?

Lazy loading nests: 1 query for the orders, 20 for their items, then one for each of the 100 items' products. That is N + N×M + 1. With the database in another zone the page now takes over a second. Batching each level keeps it at 3 queries: orders, items IN (...), products IN (...).

4. JOIN or batch?

Experiment 4 of 5
Database in another zone · 50 orders with 50 items each · one JOIN (orders × items) vs two batched queries
Which loads the page faster?

A JOIN returns one row per order-item pair, and each of those rows carries the whole order again. With 50 items per order that is 2,500 copies of 800-byte orders: over 2 MB instead of about 340 KB, so the wire time outweighs the round trip it saved. With few children per order (5, say) the JOIN wins. For one-to-many with many children, batch; for one-to-one or few, join.

5. Fire them all at once

Experiment 5 of 5
Database in another zone · 20 orders · the 20 item queries run 5 at a time on a connection pool, instead of one by one
Compared with batching the items into one query…

Running the queries in parallel hides some of the waiting: four waves of five trips instead of twenty in a row. But the page still needs those waves, it holds five connections while it runs, and the database still parses, plans and runs 21 queries per page instead of 2. At a few hundred pages a second that is thousands of extra queries a second. Batching fixes the cause; parallelism only hides the latency.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1Your list page is fast on your laptop and slow in staging. The query log shows the same SELECT many times with different ids. What is going on?
A good answer coversAn N+1: one query for the list, then one per row for its related data. Locally each round trip costs a fraction of a millisecond, so 51 queries feel free; in staging the database is a network hop away and the page pays the round trip 51 times, one after another.
Q2How would you catch N+1s before production?
A good answer coversCount queries per request: turn on ORM query logging, look at the span list in your APM or tracing (a long ladder of identical spans is the signature), and add tests that assert the query count for key endpoints so it can't silently grow with the data.
Q3Why does an ORM make N+1 so easy to write?
A good answer coversLazy relations look like plain attributes. `order.items` inside a loop or a template reads like a field access, but each first access runs a query. The code that triggers the queries (often a view or serializer) is far from the code that loaded the list.
Q4JOIN, or a second query with IN (...)? How do you choose?
A good answer coversA JOIN (eager load in one query) is great for one-to-one or a few children: one round trip, little repetition. For one-to-many with many children, the JOIN repeats the parent's columns on every child row and can multiply rows across several relations, so a separate IN (...) query per relation (prefetch) ships far less. Both are a constant number of queries per page.
Q5In a GraphQL API every field resolver loads its own data. How does DataLoader prevent N+1 there?
A good answer coversResolvers ask the loader for one key each; the loader waits until the current tick ends, collects every key requested, and runs one batched query (WHERE id IN (...)). It also caches per request, so the same key is fetched once. N resolver calls become one query per relation per level.
Q6Paging the list limits the damage. Why is it not a fix?
A good answer coversA page of 20 bounds the queries to 21 instead of thousands, but the cost still grows with page size and nesting, and every page still pays 21 round trips. The goal is a constant number of queries per request, independent of how many rows are on the page.
