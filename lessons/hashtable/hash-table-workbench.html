Hash Table WorkbenchBanco de trabajo: tablas hash

A hash table turns a key into a bucket number, so finding the key takes a jump instead of a search. That's behind every dictionary, map, set, cache and database index on hashes, and it stays fast only while keys spread out and buckets stay uncrowded. This lesson builds a hash table as a rack of trays: watch it, predict what it does, then explain it back.Una tabla hash convierte una clave en un número de cubeta, así que encontrar la clave cuesta un salto en lugar de una búsqueda. Está detrás de cada diccionario, map, set, caché e índice hash de una base de datos, y se mantiene rápida solo mientras las claves se reparten y las cubetas no se llenan demasiado. Esta lección arma una tabla hash como un casillero de bandejas: mírala, predice qué hace y después explícalo.

02

Predict, then runPredice y ejecuta

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine, at a bigger scale (1,000 keys or more), averaged over six seeded runs where the keys are random.Cada experimento cambia una sola cosa. Elige lo que esperas antes de ejecutarlo. Los resultados salen del mismo modelo que la máquina, a mayor escala (1,000 claves o más), promediados sobre seis ejecuciones con semilla fija cuando las claves son aleatorias.

1. Keep adding, never growAgrega sin parar, sin crecer nunca

Experiment 1 of 5Experimento 1 de 5
Chaining, 64 buckets, resizing off · insert 64 user ids, then 1,024 · six seeded runsEncadenamiento, 64 cubetas, sin redimensionar · inserta 64 IDs de usuario y después 1,024 · seis ejecuciones con semilla fija
What happens to the average number of keys a lookup compares?¿Qué pasa con la cantidad promedio de claves que compara una búsqueda?

A lookup hashes straight to the right bucket, then walks that bucket's chain. With 64 buckets and 1,024 keys every chain holds about 16, so a lookup compares about 9 keys on average and the unluckiest dozens. O(1) holds only while keys per bucket (the load factor) stays bounded, which is why real tables grow: the same 1,024 keys in a table that doubles at 75% average barely more than one compare.Una búsqueda va directo a la cubeta correcta con el hash y después recorre la cadena de esa cubeta. Con 64 cubetas y 1,024 claves cada cadena tiene unas 16, así que una búsqueda compara unas 9 claves en promedio y la más desafortunada, decenas. El O(1) se cumple solo mientras las claves por cubeta (el factor de carga) se mantienen acotadas; por eso las tablas reales crecen: las mismas 1,024 claves en una tabla que se duplica al 75% promedian apenas más de una comparación.

2. A hash that reads only the start of the keyUn hash que solo lee el comienzo de la clave

Experiment 2 of 5Experimento 2 de 5
1,000 user ids (user:1000 … user:9999), chaining, doubling at 75% · a good hash vs one that reads only the first 4 characters1,000 IDs de usuario (user:1000 … user:9999), encadenamiento, duplicando al 75% · un buen hash contra uno que solo lee los primeros 4 caracteres
What does the weak hash do to lookups?¿Qué le hace el hash débil a las búsquedas?

Every id starts with "user", so a hash that reads only those characters gives every key the same number, and the same number lands in the same bucket at any table size. The table still doubles (the load factor looks fine) but 2,047 buckets stay empty while one chain holds all 1,000 keys. A good hash mixes every character of the key into every bit of the result.Todos los IDs empiezan con "user", así que un hash que solo lee esos caracteres le da el mismo número a todas las claves, y el mismo número cae en la misma cubeta con cualquier tamaño de tabla. La tabla igual se duplica (el factor de carga se ve bien), pero 2,047 cubetas quedan vacías mientras una sola cadena tiene las 1,000 claves. Un buen hash mezcla cada carácter de la clave en cada bit del resultado.

3. The price of doublingEl precio de duplicar

Experiment 3 of 5Experimento 3 de 5
Insert 1,000 keys into a table that starts with 8 buckets and resizes at 75% · grow by doubling, or by adding 8 buckets each timeInserta 1,000 claves en una tabla que empieza con 8 cubetas y se redimensiona al 75% · crece duplicando, o sumando 8 cubetas cada vez
A resize moves every key into the new table. Averaged over all 1,000 inserts, how many moves does doubling cost per insert?Redimensionar mueve cada clave a la tabla nueva. Promediado sobre las 1,000 inserciones, ¿cuántos movimientos cuesta duplicar por inserción?

Doubling copies 6, then 12, 24, … 768 keys: each copy is as big as all the earlier ones together, so the total stays under twice the number of keys and each insert pays for under two moves (amortised O(1)). The single insert that triggers the last resize still moves 768 keys at once: a latency spike, which is why some stores rehash a little at a time. Growing by a fixed 8 buckets resizes far more often and costs around 80 moves per insert, a number that keeps growing with n.Duplicar copia 6, después 12, 24, … 768 claves: cada copia es tan grande como todas las anteriores juntas, así que el total queda por debajo del doble de la cantidad de claves y cada inserción paga menos de dos movimientos (O(1) amortizado). La inserción que dispara el último redimensionamiento igual mueve 768 claves de una vez: un pico de latencia, por eso algunos almacenes rehashean de a poco. Crecer de a 8 cubetas redimensiona mucho más seguido y cuesta unos 80 movimientos por inserción, un número que sigue creciendo con n.

4. Chaining or linear probing, 90% fullEncadenamiento o sondeo lineal, al 90%

Experiment 4 of 5Experimento 4 de 5
1,024 buckets, no resizing · fill to 50%, then to 90% · chaining keeps a list per bucket; linear probing puts one key per slot and tries the next slot when one is taken1,024 cubetas, sin redimensionar · llena hasta el 50% y después hasta el 90% · el encadenamiento guarda una lista por cubeta; el sondeo lineal pone una clave por casilla y prueba la siguiente si está ocupada
At 90% full, which one's lookups slow down more?Al 90%, ¿las búsquedas de cuál se vuelven más lentas?

With chaining, a 90% table still has short chains: about 1.5 compares to find a key, and a missing key checks less than one. With linear probing, a key that collides takes the next free slot, which makes the run of full slots longer, which makes the next collision more likely: runs clump (primary clustering). Finding a key takes about 5 checks and a missing key about 40. That's why open-addressing tables resize much earlier, around 50–70%, or probe more cleverly.Con encadenamiento, una tabla al 90% todavía tiene cadenas cortas: unas 1.5 comparaciones para encontrar una clave, y una clave que no está revisa menos de una. Con sondeo lineal, una clave que colisiona toma la siguiente casilla libre, lo que alarga el tramo de casillas llenas, lo que hace más probable la próxima colisión: los tramos se amontonan (agrupamiento primario, primary clustering). Encontrar una clave cuesta unas 5 revisiones y una clave que no está, unas 40. Por eso las tablas de direccionamiento abierto se redimensionan mucho antes, alrededor del 50–70%, o sondean de forma más ingeniosa.

5. Keys crafted to collideClaves hechas para colisionar

Experiment 5 of 5Experimento 5 de 5
The hash function is public and unseeded · an attacker searches for 1,000 keys whose hashes end in the same 11 bits and sends them all · then the same keys against a hash seeded with a secretLa función hash es pública y sin semilla · un atacante busca 1,000 claves cuyos hashes terminan en los mismos 11 bits y las envía todas · después, las mismas claves contra un hash con una semilla secreta
How much more work is inserting the crafted keys than ordinary ones?¿Cuánto más trabajo cuesta insertar las claves fabricadas que unas normales?

All the crafted keys share a bucket at every table size, so each insert compares against every key before it: 1 + 2 + … + 1,000, about half a million compares, where ordinary keys take about three thousand. A few kilobytes of request can pin a CPU (hash flooding, the 2011 attacks on web frameworks' form parsers). The seed is the fix: with a secret mixed into the hash the attacker can't predict which keys collide, so the same keys spread out normally. Python, Ruby and Rust seed their hashes per process; Java turns long chains into trees.Todas las claves fabricadas comparten cubeta con cualquier tamaño de tabla, así que cada inserción compara con todas las claves anteriores: 1 + 2 + … + 1,000, cerca de medio millón de comparaciones, donde unas claves normales cuestan unas tres mil. Unos pocos kilobytes de solicitud pueden saturar una CPU (hash flooding, los ataques de 2011 contra los analizadores de formularios de los frameworks web). La solución es la semilla: con un secreto mezclado en el hash, el atacante no puede predecir qué claves colisionan, así que las mismas claves se reparten normalmente. Python, Ruby y Rust usan una semilla por proceso; Java convierte las cadenas largas en árboles.

03

Explain it backExplícalo

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.Responde en voz alta o por escrito antes de abrir cada una. Funcionan bien en pareja: una persona explica y la otra pregunta "¿por qué?" dos veces.

Q1P1Why is a hash table lookup "O(1) on average", and what has to be true for that to hold?¿Por qué una búsqueda en una tabla hash es "O(1) en promedio", y qué tiene que cumplirse para que sea así?
A good answer coversUna buena respuesta cubreThe hash jumps straight to one bucket, so the work is the length of that one chain (or probe run), not the size of the table. That stays constant only if the hash spreads keys evenly and the table keeps the load factor bounded by growing. It's an average: a bad hash, unlucky or crafted keys, or a full table make single lookups slow.El hash salta directo a una cubeta, así que el trabajo es el largo de esa cadena (o tramo de sondeo), no el tamaño de la tabla. Eso se mantiene constante solo si el hash reparte las claves de forma pareja y la tabla mantiene acotado el factor de carga creciendo. Es un promedio: un hash malo, claves con mala suerte o fabricadas, o una tabla llena vuelven lentas búsquedas individuales.
Q2P2What is the load factor, and why does a table resize at a limit instead of when it's completely full?¿Qué es el factor de carga, y por qué una tabla se redimensiona en un límite en lugar de cuando está completamente llena?
A good answer coversUna buena respuesta cubreKeys divided by buckets. Expected chain length grows with it, and probe runs grow much faster as it nears 1 (roughly 1/(1−α)² for a missing key with linear probing). Resizing at around 0.75 for chaining, or 0.5–0.7 for open addressing, keeps lookups short at the cost of some empty buckets.Las claves divididas por las cubetas. El largo esperado de las cadenas crece con él, y los tramos de sondeo crecen mucho más rápido cuando se acerca a 1 (más o menos 1/(1−α)² para una clave que no está, con sondeo lineal). Redimensionar alrededor de 0.75 con encadenamiento, o 0.5–0.7 con direccionamiento abierto, mantiene cortas las búsquedas a cambio de algunas cubetas vacías.
Q3P3Doubling makes one insert copy every key. Why is the cost per insert still constant on average, and when does the spike still hurt?Duplicar hace que una inserción copie todas las claves. ¿Por qué el costo por inserción sigue siendo constante en promedio, y cuándo el pico igual duele?
A good answer coversUna buena respuesta cubreEach resize copies as many keys as all previous resizes together, so total copying is under 2n for n inserts: amortised O(1). Growing by a fixed amount would make it O(n) per insert. The spike is a single slow operation, which matters for latency-sensitive paths; some systems (Redis, for example) rehash incrementally, moving a few buckets per operation while both tables live.Cada redimensionamiento copia tantas claves como todos los anteriores juntos, así que el copiado total queda por debajo de 2n para n inserciones: O(1) amortizado. Crecer en una cantidad fija lo volvería O(n) por inserción. El pico es una sola operación lenta, lo que importa en caminos sensibles a la latencia; algunos sistemas (Redis, por ejemplo) rehashean de forma incremental, moviendo unas pocas cubetas por operación mientras conviven las dos tablas.
Q4P4Compare chaining with open addressing (linear probing). What does each do well?Compara el encadenamiento con el direccionamiento abierto (sondeo lineal). ¿Qué hace bien cada uno?
A good answer coversUna buena respuesta cubreChaining tolerates high load factors and simple deletes, but follows pointers to separate nodes (cache misses, extra memory). Linear probing keeps keys in one array, so a probe run is a fast sequential scan, but it clusters as the table fills, must resize earlier, and deletes need tombstones or shifting. Many modern tables use open addressing with smarter probing (Robin Hood, SwissTable).El encadenamiento tolera factores de carga altos y borrados simples, pero sigue punteros a nodos separados (fallos de caché, más memoria). El sondeo lineal guarda las claves en un solo arreglo, así que un tramo de sondeo es un recorrido secuencial rápido, pero se agrupa a medida que la tabla se llena, tiene que redimensionarse antes y los borrados necesitan lápidas (tombstones) o desplazamientos. Muchas tablas modernas usan direccionamiento abierto con sondeos más ingeniosos (Robin Hood, SwissTable).
Q5P5What makes a hash function good for a hash table? Why didn't resizing rescue the weak hash?¿Qué hace que una función hash sea buena para una tabla hash? ¿Por qué redimensionar no rescató al hash débil?
A good answer coversUna buena respuesta cubreIt's fast, deterministic for equal keys, and mixes every part of the key into every bit of the output, so similar keys (shared prefixes, sequential ids) land far apart. Resizing only changes how many low bits pick the bucket; if keys produce the same hash, they collide at every size.Es rápida, da lo mismo para claves iguales y mezcla cada parte de la clave en cada bit del resultado, así que claves parecidas (prefijos comunes, IDs consecutivos) caen lejos entre sí. Redimensionar solo cambia cuántos bits bajos eligen la cubeta; si las claves producen el mismo hash, colisionan con cualquier tamaño.
Q6P6What is hash flooding, and how do languages and frameworks defend against it?¿Qué es el hash flooding, y cómo se defienden los lenguajes y los frameworks?
A good answer coversUna buena respuesta cubreAn attacker who can predict the hash sends many keys that collide (form fields, JSON keys, headers), turning each insert into a scan and the request into O(n²) CPU. Defences: a keyed hash with a per-process random seed (SipHash in Python, Rust and Ruby), limits on how many keys a request may carry, and tree-shaped buckets once a chain gets long (Java's HashMap).Un atacante que puede predecir el hash envía muchas claves que colisionan (campos de formulario, claves JSON, encabezados), y convierte cada inserción en un recorrido y la solicitud en CPU O(n²). Defensas: un hash con clave y una semilla aleatoria por proceso (SipHash en Python, Rust y Ruby), límites a cuántas claves puede traer una solicitud y cubetas en forma de árbol cuando una cadena se alarga (el HashMap de Java).
