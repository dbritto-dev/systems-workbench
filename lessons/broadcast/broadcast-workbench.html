Systems lesson 18 · Broadcast

Broadcast Workbench

Broadcast means every node learns every value. Which nodes talk to which (the topology) decides how many messages that costs and how long it takes. This lesson builds that idea three ways: watch a machine do it, predict what breaks it, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine: 25 nodes, 100 values a second for 20 s, 100 ms per message.

1. Pick a topology

Experiment 1 of 5
Grid → ring → hubs · 25 nodes, 100 values a second, 100 ms per message
Challenge 3d asks for fewer than 30 messages per value, a median under 400 ms and a maximum under 600 ms. Which topology meets it?

Flooding a grid sends every value down almost every wire (56 messages), and the far corner is 8 hops away (800 ms). A ring is cheap but slow: halfway round is 12 hops. Hubs keep every node within 3 hops of every other and send each value down each wire once. Sending straight from the first node to all 24 others also passes, but it needs every node connected to every other, which stops working long before 1,000 nodes.

2. Batch the messages

Experiment 2 of 5
Hubs · batching off → one message per neighbour every 200 ms
Challenge 3e asks for fewer than 20 messages per value, a median under 1 s and a maximum under 2 s. With batching every 200 ms…

At 100 values a second, a node has several new values each time it flushes, so one message carries many of them. Each value waits for the next flush at every hop, so latency grows with the batch interval. 200 ms is comfortably inside 3e; 500 ms pushes the median past 1 s. Batching trades latency for messages, the same deal as Kafka's linger.ms or Nagle's algorithm in TCP.

3. Cut the network

Experiment 3 of 5
Hubs · the fence goes up between columns 2 and 3 for 3 seconds · no retries
What happens to the values sent while the network is cut?

A message sent across the cut is simply lost, and nobody sends it again, so values that started on one side never reach the other. Maelstrom's checker catches this as values missing from reads. Retrying every unacknowledged message until it is acknowledged gets everything through after the cut heals, at a price: every message now has an acknowledgement, so messages per value more than double.

4. Lose a hub

Experiment 4 of 5
Hubs · the top-left hub is switched off
Which nodes stop hearing new values?

In the hub topology each leaf has exactly one path to the rest of the network: its hub. When the hub dies, its leaves are cut off in both directions. The grid has many paths between any two nodes, so the same failure costs it nothing. Fewer wires means fewer messages and fewer ways round a failure; production systems keep two parents per node or fall back to gossip.

5. Forward everything

Experiment 5 of 5
Grid · forward every copy you receive, not only values you haven't seen
One value enters the network. How many messages in the first second?

Every node that forwards every copy turns one incoming message into three outgoing ones, and the grid has loops, so copies come back round and multiply at every hop. Remembering which values you've already seen makes forwarding idempotent: a second copy is ignored. Real systems do the same with message IDs, sequence numbers or a hop limit.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1The grid Maelstrom gives you connects every node. Why does flooding it fail challenge 3d?
A good answer coversFlooding sends each new value to every neighbour except the sender, so a value crosses nearly every wire: 56 messages for 25 nodes. And the grid is wide: the far corner is 8 hops away, 800 ms at 100 ms a hop. Connected is not the same as short or cheap.
Q2Sending straight from the first node to all 24 others gives 24 messages and 100 ms. Why not always do that?
A good answer coversEvery node needs a connection to every other one: 300 links for 25 nodes, about 500,000 for 1,000. Each node also has to know the full membership. Relays such as hubs keep each node's fan-out small and the path short, which is what scales.
Q3What does batching trade, and where else have you seen the same trade?
A good answer coversIt trades latency for messages: values wait up to one interval at each hop, and one message carries many values. Kafka producers (linger.ms, batch size), Nagle's algorithm in TCP and log shippers all do the same.
Q4Retries delivered everything across a cut network but doubled messages per value. Why, and how do real systems keep that down?
A good answer coversEvery message needs an acknowledgement, and unacknowledged ones are sent again. Systems acknowledge in batches, back off between retries, or skip per-message acks and periodically compare what each side has (anti-entropy), sending only the difference.
Q5A hub dies and its branch goes dark. How would you design so one node can't cut off others?
A good answer coversGive every node at least two independent paths: two parents, a ring of hubs with leaves connected to two hubs, or a gossip fallback. Detect the failure (heartbeats) and rewire around it.
Q6Why must a node forward only values it hasn't seen?
A good answer coversNetworks with loops send copies back round. If every copy is forwarded, they multiply without end. Keeping a set of seen value IDs makes handling a duplicate a no-op. That's idempotency, the same idea as idempotency keys on an API.
