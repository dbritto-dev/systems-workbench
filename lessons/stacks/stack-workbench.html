Systems lesson 34 · Stacks

Stack Workbench

A stack hands back the last thing you put on it: last in, first out. It runs every function call you make, it is how undo works, and under overload it can decide which users get an answer. This lesson builds three stacks on one machine: watch them, predict what they do, then explain it back.

02

Predict, then run

Each experiment changes one thing. Choose what you expect before running it. Results come from the same model as the machine; the server experiment is averaged over six seeded runs.

1. A function that calls itself

Experiment 1 of 5
sum(5) = 5 + sum(4), …, down to sum(1) = 1 · every call waits for the one it made
How deep does the call stack get, and which call returns first?

Each call pushes a frame and can't finish until the call it made returns, so the frames pile up: sum(5) at the bottom, sum(1) on top. The last call made is the first to return (last in, first out), and each return hands its result down to the frame underneath.

2. Recursion that goes too deep

Experiment 2 of 5
The same sum, n = 5,000 · the stack has room for 1,000 frames · then the same sum written as a loop
What happens to the recursive version?

The call stack is a fixed-size block of memory per thread, so depth is capped (in browsers and Node around ten thousand frames, in Python 1,000 by default). Every frame is still waiting when the next is pushed, so 5,000 nested calls can't fit. The loop keeps one frame and a running total: depth 1 for any n. Iteration, or an explicit stack in an array on the heap, removes the limit.

3. Undo twice, then type

Experiment 3 of 5
Type A, B, C · undo twice (C and B move to the redo stack) · then type D
What can Redo bring back now?

Undo pops the top edit and pushes it on the redo stack; redo does the reverse. A new edit starts a different future, so the old redo stack no longer applies and is thrown away. Browsers do the same with back and forward: visiting a new page from the middle of your history drops the forward list.

4. Walking a tree with a stack

Experiment 4 of 5
Tree: 1 has children 2 and 3; 2 has 4 and 5; 3 has 6 and 7 · keep the nodes still to visit on a stack (or let recursion do it)
Which node is visited right after node 2?

Taking the most recent node first goes deep before wide: 2's children were pushed after 3, so they come off first. That is depth-first search, and it is what recursion does with the call stack. Swap the stack for a queue (take the oldest first) and the same loop visits level by level: breadth-first.

5. Overloaded: newest first or oldest first?

Experiment 5 of 5
Requests arrive at 120% of what the worker can finish · clients give up after 1 s · 60 s, six seeded runs
What share of requests finish before their client gives up?

With more work than capacity, the backlog only grows. Taking the oldest first means every request waits behind the whole backlog, so after a few seconds everything finishes too late: the worker is at 100% doing work nobody is waiting for. Taking the newest first serves fresh requests in time and lets the old ones starve at the bottom. That is why some servers switch to newest-first only when the queue is long (adaptive LIFO), and drop requests past their deadline.

03

Explain it back

Answer out loud or in writing before opening each one. These work well as a pairing exercise: one person explains, the other asks "why?" twice.

Q1A function calls itself ten levels deep. What is on the call stack at the deepest point, and in what order do the calls finish?
A good answer coversTen frames, one per call still in progress, each holding its arguments, local variables and where to return to. The deepest (last) call is on top and finishes first; each return pops its frame and hands the result to the frame underneath.
Q2Why does deep recursion crash with "Maximum call stack size exceeded" or StackOverflowError, and what are two ways to fix it?
A good answer coversEach thread's call stack is a fixed, fairly small block of memory, so only so many frames fit. Fixes: rewrite as a loop, or keep your own stack (an array on the heap) of work still to do; or reduce depth (divide and conquer, a balanced structure). Raising the limit only moves the cliff.
Q3Explain undo and redo as two stacks. Why does a new edit clear redo?
A good answer coversEvery edit is pushed on the undo stack. Undo pops it, reverses it, and pushes it on redo; redo does the opposite. A new edit branches history: the redone edits were made on top of a document that no longer exists, so they are discarded.
Q4Where is the stack in a browser's back and forward buttons, and in an iterative depth-first search?
A good answer coversBack is a stack of pages you came from and forward a stack of pages you went back from; visiting a new page clears forward. Iterative DFS keeps a stack of nodes still to visit: pop one, push its children, repeat.
Q5Under overload, why can serving the newest request first give more successful responses than first come, first served? What does it cost, and how do real systems limit the damage?
A good answer coversWhen the backlog grows, the oldest requests have usually already timed out on the client; serving them first is wasted work while fresh ones wait and time out too. Newest-first keeps serving requests someone still wants, at the cost of starving the oldest. Systems use it only when the queue is long (adaptive LIFO), cap the queue, and drop requests whose deadline has passed.
Q6When do you want a queue instead of a stack?
A good answer coversWhen order and fairness matter: jobs that must all be done, messages processed in the order sent, requests under normal load (first come, first served keeps waits even and predictable), and breadth-first search. A stack fits nested work (calls, undo, parsing brackets) and freshness-first under overload.
